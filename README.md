Бот для Telegram: AI-чат с персонами и памятью. Игры и гороскоп перенесены в `Fun-Telegram-Bot`.

Команды:

- `/ai` — Спросить ИИ
- `/clear` — Обнулить память AI (с подтверждением)

## Запуск

Требуется JDK 17. Сборка из корня репозитория собирает три модуля — `core`, `bot`, `admin` — и даёт два jar: `bot/target/telegram-bot-1.0.jar` и `admin/target/telegram-bot-admin-1.0.jar`.

```
mvn clean package
```

Бот запускается headless, без HTTP-порта; админка — отдельный процесс на своём порту. Переменные админки и её запуск описаны в `admin/README.md`, бота — в `bot/README.md`.

Конфигурация передаётся только переменными окружения — позиционные аргументы командной строки не поддерживаются (они видны в `ps` любому локальному пользователю):

| Переменная | Значение |
|---|---|
| `BOT_TOKEN` | токен бота |
| `BOT_DB_URL` | JDBC-URL базы |
| `BOT_DB_USER` | пользователь базы |
| `BOT_DB_PASSWORD` | пароль базы |
| `BOT_AI_KEY_<ID>` | ключ провайдера: `BOT_AI_KEY_DEEPSEEK`, `BOT_AI_KEY_GROK`, `BOT_AI_KEY_OPENAI`, `BOT_AI_KEY_GEMINI`, `BOT_AI_KEY_MISTRAL`, `BOT_AI_KEY_AITUNNEL`, `BOT_AI_KEY_VENICE`, `BOT_AI_KEY_ABLITERATION`; ни один ключ не обязателен |
| `BOT_ADMIN_PASSWORD` | пароль владельца и выключатель веб-админки; без него админка выключена |
| `BOT_ADMIN_PORT` | порт админки, по умолчанию `8081` |
| `BOT_ADMIN_BIND` | адрес админки, по умолчанию `127.0.0.1`; на сервере `0.0.0.0` вместе с правилом файрвола |

Windows (cmd):

```
set BOT_TOKEN=<token>
set BOT_DB_URL=jdbc:postgresql://host:5432/db
set BOT_DB_USER=<dbUser>
set BOT_DB_PASSWORD=<dbPassword>
set BOT_AI_KEY_DEEPSEEK=<aiKey>
java -jar bot/target/telegram-bot-1.0.jar
```

Linux:

```
BOT_TOKEN=<token> BOT_DB_URL=jdbc:postgresql://host:5432/db \
BOT_DB_USER=<dbUser> BOT_DB_PASSWORD=<dbPassword> BOT_AI_KEY_DEEPSEEK=<aiKey> \
java -jar bot/target/telegram-bot-1.0.jar
```

Обязательные переменные проверяются при старте: если значение пустое или не задано, приложение завершается с ненулевым кодом и сообщением, в котором указано имя переменной, не подключаясь к базе и Telegram.

## Уведомление о запуске

После старта бот присылает владельцу сообщение в личку: время запуска, часовой пояс, имя хоста, модель, температуру и лимит токенов для ответов. Получатель задаётся настройкой `ownerChatId` в таблице `bot_settings` — это Telegram ID пользователя (в личном чате `chat_id` совпадает с `user_id`). Если настройка отсутствует, пуста или содержит не число, уведомление не отправляется, а в лог пишется `WARN`.

```sql
INSERT INTO public.bot_settings (setting_key, value, description)
VALUES ('ownerChatId', '<telegram user id>', 'Кому присылать уведомления о запуске')
ON CONFLICT (setting_key) DO UPDATE SET value = EXCLUDED.value;
```

## Персона в «синем» чате

В чате `-1001347887839` отвечает персона «Юра». Её характер хранится в таблице `personas` (поле `prompt`), имена для обращения — в `persona_aliases`, привязка чата к персоне — в `chat_personas`. Промпт читается из базы на каждый запрос, поэтому правка применяется без перезапуска бота.

Сообщение без слэша вызывает ответ персоны, если:

- в нём есть алиас персоны как отдельное слово в любом месте сообщения: «юра, привет», «как дела, юра?». Слова вроде «юрист» и «юрта» обращением не считаются;
- сообщение является ответом (реплаем) на сообщение самого бота — имя в тексте не нужно.

Модели уходит исходный текст сообщения целиком. Если в сообщении только обращение, бот просит задать вопрос. Слэш-команды `/ai`, `/ии`, `/аи` работают в любом чате как раньше.

Промпт персоны заполняет раздел «Персона» системного промпта; в чате без персоны там `aiPromtContext`, а при отсутствии настройки — дефолтный промпт. Остальные разделы (техника, люди, время, формат ответа) собираются и в чате с персоной, и без неё.

Автор сообщения хранится в `ai_messages` отдельно от текста — `author_user_id`, `author_nick`, `author_name`; подпись «@ник (Имя)» формируется при сборке запроса. Поэтому в истории нет служебного префикса, а раздел «Люди» знает, кто писал, даже если ник в Telegram изменился.

## Ответ персоны

Ответ строится в два запроса. Первый — **план**: тема, намерение (`question`, `remark`, `insult`, `apology`, `ignore`), выбранные воспоминания, сдвиги эмоций с пояснением, число реплик и адресаты колкостей. Второй — **генерация**: модель получает план и возвращает JSON-массив реплик. Оба шага пишут в лог длительность, тему, намерение и число реплик. Если план не получен или не разобрался, бот отвечает одним запросом, как раньше.

Реплики уходят по одной с паузой `replyDelayMs` (в карточке персоны), их число ограничено `maxReplies`; лишние и пустые отбрасываются. Каждая реплика сохраняется в историю отдельно. Намерение `ignore` означает, что бот не отвечает.

**Настроение.** После отправки бот применяет сдвиги из плана к действующим значениям эмоций: не больше ±3 за ход, ограничение 0..10, `updated_at` обновляется. Следующий ответ строится уже по новому состоянию. Коды эмоций берутся из справочника, неизвестные игнорируются.

**Обиды.** Оскорбление в адрес персоны повышает обиду на автора и гнев, извинение снимает обиду. Обида хранится в `persona_grudges` с ключом «чат + участник» и затухает по времени. Пока действующая сила не ниже порога, участник может быть адресатом колкостей. Прибавки и порог — `aiGrudgeInsultStrength`, `aiGrudgeAngerDelta`, `aiGrudgeDecayPerHour`, `aiGrudgeThreshold` на вкладке «Память».

**Срыв.** Если агрессия не ниже `aggressionThreshold` и в этом ходе пришло новое оскорбление, персона отвечает `hysteriaReplies` репликами всем, кто писал последние 50 сообщений. После срыва гнев возвращается к базовому значению, обида остаётся, а следующий срыв возможен не раньше `hysteriaCooldownHours` часов. Стиль срыва задаёт промпт персоны.

## Память персоны

Воспоминания лежат в `persona_memories`: категория из справочника `memory_categories`, текст, важность 1–10, дата события (может быть пустой), источник (`auto` — создал анализ, `manual` — человек) и признак ядра `is_core`. Люди, упомянутые в воспоминании, связываются через `memory_people` по Telegram `user_id`.

Раз в 5 минут бот проверяет чаты с персонами: если после отметки в `memory_analysis_state.last_message_id` накопилось `aiMemoryAnalyzeEvery` (старт 50) новых сообщений, отдельным запросом к модели извлекаются факты. Промпт анализа задаётся настройкой `aiMemoryExtractPrompt`, в один запрос уходят последние `aiMemoryAnalysisMessages` (старт 50) сообщений, а на ответ модели отводится `aiMemoryAnalysisMaxTokens` токенов (старт 8000). Изменения памяти и отметка пишутся одной транзакцией: при ошибке модели или невалидном ответе память не меняется, а отметка не сдвигается.

В анализ уходят существующие воспоминания с датой обновления и новые сообщения с датой и автором. Поэтому изменившийся факт (новая работа, машина, город) модель оформляет как `update` с его `id`, а прямо опровергнутый — как `delete`. Основание — слова самой персоны или согласованные сообщения нескольких участников; подколы и чужие утверждения без подтверждения не считаются.

Ядровые воспоминания (`is_core = true`) создаются только вручную, удалять их анализ не может (попытка логируется), а обновлять — может. Ручные записи (`source = 'manual'`) от удаления тоже защищены. Ядро всегда и целиком попадает в системный промпт; обычные воспоминания — не более `aiMemoryPromptSize` (старт 30) штук, по важности, затем по свежести события.

Анализируется только то, что осталось в окне истории (`aiHistorySize`, 100 сообщений). Если бот долго не работал и часть переписки выпала, в лог пишется предупреждение с отметкой анализа и границами доступного окна.

## Веб-админка

Админка — отдельный jar и отдельный процесс: перезапуск страниц не прерывает ответы бота, а правки из админки применяются к следующему запросу без перезапуска бота.

Вход открыт только по двум адресам: loopback (SSH-туннель владельца) и VPN-подсеть `10.8.0.0/24`. На сервере приложение слушает `BOT_ADMIN_BIND=0.0.0.0`, а доступ ограничивает правило файрвола на порт `8081`:

```
# nftables/iptables: пропустить 8081 только с loopback и из туннеля
nft add rule inet filter input tcp dport 8081 ip saddr { 127.0.0.1, 10.8.0.0/24 } accept
nft add rule inet filter input tcp dport 8081 drop
```

Без этого правила админка с паролем окажется в интернете — правило накатывается вместе с выкаткой, а не «потом». Публичного HTTPS-входа и домена нет.

Профили модераторов собираются из OpenVPN-сервера на том же хосте (`udp 1194`, `tun0 10.8.0.1/24`) **без** `redirect-gateway def1`: иначе весь трафик телефона уйдёт через сервер, где Telegram режется DPI, и модератор потеряет доступ к боту. В профиле остаётся только маршрут в туннельную подсеть.

Включение — паролем в окружении:

```
set BOT_ADMIN_PASSWORD=<пароль>
java -jar admin/target/telegram-bot-admin-1.0.jar
```

Без `BOT_ADMIN_PASSWORD` админских страниц не существует: `/admin/**` отвечает 404, в лог пишется `WARN`.

### Два вида учёток

- **Владелец** — логин `admin`, пароль из `BOT_ADMIN_PASSWORD`; видит все разделы. Сессия HttpOnly, CSRF включён, выход кнопкой (POST).
- **Модератор** — учётка в базе, привязанная к человеку из `tg_users`; логин и пароль выдаёт владелец в разделе «Модераторы». Логин `admin` зарезервирован, пароли хранятся только хешем.

Владелец на проде открывает админку туннелем:

```
ssh -L 8081:127.0.0.1:8081 <user>@<host>
```

и затем в браузере `http://127.0.0.1:8081/admin/login`. Модератор подключается VPN-профилем и открывает `http://10.8.0.1:8081/admin/login`.

### Модераторы

Раздел `/admin/moderators` — единственное место, где создаётся учётка и выдаётся чат. Создание: человек (`@ник` из чата или Telegram id), логин, пароль не короче шести символов. Смена пароля и удаление учётки — там же; удаление сразу отзывает вход, отдельного отзыва сертификата не требуется.

Права модератора:

- видит только выданные чаты, в «Чатах» у него нет выбора чата;
- правит персону, пока **все** её чаты выданы ему; если владелец привязал персону к своему чату, карточка открывается только для чтения;
- видит и правит воспоминания только своих персон; память общей персоны не показывается;
- создаёт новую персону сразу вместе с привязкой к своему чату — беспризорных персон у него не бывает;
- «Промпт», «Эмоции» (справочник), «Настройки» и «Модераторы» закрыты на сервере, а не только скрыты в меню.

Вкладка «Эмоции» в карточке персоны модератору доступна: это характер его персоны, а не справочник. Всё меню — «Персоны», «Воспоминания», «Чаты».

### Удаление воспоминаний

Удаление мягкое: запись исчезает из списка и из промпта, но остаётся в таблице (`deleted_at`). Вернуть её можно в разделе «Воспоминания», включив фильтр «удалённые» и нажав «Восстановить». Удаление персоны вместе с её памятью необратимо.

### Персоны

Страница `/admin/personas` — список персон с числом алиасов, воспоминаний и привязанными чатами. Карточка правит имя, промпт, алиасы и настройки эмоциональности; изменения применяются к следующему запросу, потому что промпт и алиасы читаются из БД каждый раз.

Проверки карточки: имя и промпт непустые, имя уникально; алиас — одно слово, не совпадает с командой бота (`clear`, `ai`, `bot_info`, `help` и т. д.) и не занят другой персоной. Имена-обращения `юра`, `юрий`, `юрец` разрешены: по ним и так вызывается персона.

Персону, привязанную к чату, удалить нельзя — страница покажет эти чаты, сначала снимите привязку в разделе «Чаты». Свободная персона удаляется вместе с алиасами и памятью после подтверждения.

Настройки эмоциональности (шкалы 0..10, порог срыва, число ответов при срыве, задержка, инициатива) хранятся в карточке, но на ответы пока не влияют — это задача #51.

### Воспоминания

Страница `/admin/memories` показывает, что персона помнит: фильтры по персоне, категории, человеку, тексту, признаку ядра и удалённым записям, порядок по важности или по дате события, по 25 записей на страницу. Ядровые записи помечены бейджем «ядро».

Карточка правит текст, категорию, важность 1..10, дату события, связанных людей и признак ядра; источник показан только для чтения. Ручное добавление сохраняется с `source = 'manual'`, и автоматический анализ такую запись удалить не может. Снятие признака ядра превращает запись в обычную.

Удаление идёт через отдельную страницу подтверждения; для ядровой записи там предупреждение, что анализ её не восстановит. Сама запись при этом не теряется: она помечается удалённой и возвращается из списка «удалённые».

### Чаты

Страница `/admin/chats` показывает известные боту чаты, их текущую персону и дату привязки. Сохранение выбора назначает персону, меняет её или снимает привязку.

- **Первое назначение** очищает историю и записывает строку о входе в `ai_messages`.
- **Смена персоны** очищает историю диалога, чтобы новая персона начала разговор заново, и пишет строку о входе. Память персон и отметка разобранных сообщений не трогаются, счётчик сбросов не растёт.
- **Снятие** удаляет привязку; история остаётся, чат работает с промптом из настроек.
- **Повторное назначение той же персоны** ничего не меняет.

В Telegram при этом ничего не отправляется: админка не подключается к Telegram.

Перед сохранением смены персоны страница показывает, сколько сообщений истории будет стёрто. Предупреждение появляется только когда выбрана другая персона и в чате есть сообщения; откат историю не восстанавливает, поэтому решение принимается до нажатия.

### Промпт

Страница `/admin/prompt` показывает разделы системного промпта в том порядке, в котором они уходят модели: техника, персона, эмоции, обиды, память, люди, время, формат ответа. Порядок и бюджеты заданы в коде, поэтому настройкой их не поменять. В списке чатов для предпросмотра две группы: с персоной и без неё.

У каждого раздела — поле шаблона, счётчик символов рядом с бюджетом и кнопка «вернуть по умолчанию»; текст персоны правится в её карточке. Пустой раздел не попадает в промпт вместе с заголовком. Техника и персона при превышении бюджета не обрезаются — в лог пишется предупреждение.

Кнопка «Предпросмотр» собирает промпт на реальных данных выбранного чата: персону, эмоции, память, участников и текущее время. Предпросмотр ничего не пишет в базу. Участники берутся из авторов последних 50 сообщений, не больше 10 строк, автор текущего вопроса помечен как «сейчас пишет».

### Эмоции

Страница `/admin/emotions` правит справочник: подпись, вес в агрессию (от -1 до 1), скорость затухания и базовое значение (0..10), а также фразу для каждой полосы значения — 0-1, 2-4, 5-6, 7-8, 9-10. Производная агрессия не редактируется: она считается из остальных эмоций.

Текст фразы попадает в раздел «Эмоции», когда значение эмоции оказывается в этой полосе; правка действует со следующего ответа.

### Настройки

Страница `/admin/settings` правит параметры в `bot_settings`. Бот читает их на каждый запрос, поэтому сохранённое значение действует со следующего сообщения без перезапуска.

- **Модель:** `aiRoute` — дверь к модели (провайдер из каталога; пустое значение означает «провайдер выбранной модели»), `aiModel` (по умолчанию `deepseek-flash`), `aiAnswerTemperature` (0..2), `maxTokensQuestion` (1..8192), `aiPlanMaxTokens` — бюджет шага «план» (1..8192), `aiMemoryAnalysisMaxTokens` (1..8192) и `aiMemoryAnalysisMessages` (1..1000) — бюджет и размер запроса анализа памяти, `aiHistorySize` — размер истории чата.
- **Выбор модели в админке:** радиокнопки «Прямой доступ» (список моделей прямых поставщиков с группами) и «Провайдеры» (каскад провайдер → группа → модель). Через провайдеров доступны агрегаторы AITunnel, Venice и Abliteration; без ключа провайдер виден с пометкой и не выбирается.
- **Память:** `aiMemoryPromptSize` (0 — в промпт идёт только ядро), `aiMemoryAnalyzeEvery` — порог фонового анализа, `aiMemoryExtractPrompt` — промпт анализа, `aiGrudgeInsultStrength`, `aiGrudgeAngerDelta`, `aiGrudgeDecayPerHour`, `aiGrudgeThreshold` — прибавки и затухание обид.
- **Промпты:** `aiPromtContext` — запасной промпт для чата без персоны. Шаблоны разделов системного промпта правятся на странице «Промпт».
- **Уведомления:** `ownerChatId` — Telegram ID получателя сообщения о запуске; пустое поле выключает уведомления.

Значение с ошибкой не сохраняется, ошибка показывается у поля. Каждое изменённое значение пишется в лог по ключу, без содержимого промптов: там реальные имена участников.

Ключи `aiSummaryTemperature` и `aiPromtSummaryContext` удалены миграцией `005_admin_panel.sql`: команда `/summary` не реализована, и эти настройки никто не читал.

## Подключение к Telegram через прокси или VPN

Прокси опционален и задаётся переменными окружения. Если `BOT_PROXY_HOST` не задан — бот подключается к Telegram напрямую (это работает, если включён системный VPN в режиме TUN).

Переменные:

| Переменная | Описание |
|---|---|
| `BOT_PROXY_TYPE` | `HTTP` (по умолчанию) или `SOCKS5` |
| `BOT_PROXY_HOST` | Хост прокси; пусто/не задано — прямое подключение |
| `BOT_PROXY_PORT` | Порт прокси |
| `BOT_PROXY_USER` | Логин прокси (опционально) |
| `BOT_PROXY_PASS` | Пароль прокси (опционально) |

### Без прокси (системный VPN в режиме TUN)

```
java -jar bot/target/telegram-bot-1.0.jar
```

### HTTP-прокси (например, локальный прокси VPN-клиента)

Windows (cmd):

```
set BOT_PROXY_TYPE=HTTP
set BOT_PROXY_HOST=127.0.0.1
set BOT_PROXY_PORT=12334
java -jar bot/target/telegram-bot-1.0.jar
```

Linux:

```
BOT_PROXY_TYPE=HTTP BOT_PROXY_HOST=127.0.0.1 BOT_PROXY_PORT=12334 \
java -jar bot/target/telegram-bot-1.0.jar
```

### SOCKS5-прокси (например, на VPS)

```
BOT_PROXY_TYPE=SOCKS5 \
BOT_PROXY_HOST=<socks-host> \
BOT_PROXY_PORT=<socks-port> \
BOT_PROXY_USER=<login> \
BOT_PROXY_PASS=<password> \
java -jar bot/target/telegram-bot-1.0.jar
```

В CI/CD эти же переменные передаются из GitHub Secrets.

## Деплой

Два workflow: `deploy-bot.yml` собирает и выкатывает `telegram-bot-1.0.jar`, `deploy-admin.yml` — `telegram-bot-admin-1.0.jar`. Изменение в `core/**` или `pom.xml` запускает оба; изменение только в `admin/**` не перезапускает бота, а только в `bot/**` — не трогает админку. Документация (`**/*.md`, `openspec/**`, `.agents/**`) деплой не запускает.

Юниты и шаблоны окружения: `deploy/telegram-bot.service`, `deploy/telegram-bot-admin.service`, `deploy/bot.env.example`, `deploy/admin.env.example`.
