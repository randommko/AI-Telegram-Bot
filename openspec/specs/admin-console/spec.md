# admin-console Specification

## Purpose
Отдельное веб-приложение админки: включение паролем из окружения, вход администратора и модераторов, навигация по разделам и доступ только через loopback и VPN-подсеть.

## Requirements

### Requirement: Админка включается паролем из окружения

Система SHALL обслуживать раздел `/admin/**` только при заданной переменной `BOT_ADMIN_PASSWORD`. Если переменная пуста или отсутствует, запросы к `/admin/**` MUST получать ответ 404, а в лог MUST писаться предупреждение; работа бота при этом MUST NOT меняться.

#### Scenario: Пароль задан

- **WHEN** приложение запущено с непустым `BOT_ADMIN_PASSWORD`
- **THEN** `/admin/login` отдаёт страницу входа, а остальные разделы админки требуют аутентификации

#### Scenario: Пароль не задан

- **WHEN** приложение запущено без `BOT_ADMIN_PASSWORD`
- **THEN** любой запрос к `/admin/**` возвращает 404, в лог пишется предупреждение, бот продолжает отвечать в чатах

### Requirement: Единственный администратор входит по паролю

Система SHALL аутентифицировать одного пользователя `admin` паролем из `BOT_ADMIN_PASSWORD` через форму входа и MUST NOT пускать неаутентифицированные запросы ни в один раздел админки. Сессия MUST быть HttpOnly, а изменения MUST приниматься только с действительным CSRF-токеном.

#### Scenario: Запрос без сессии

- **WHEN** неаутентифицированный браузер открывает любой адрес `/admin/**`, кроме страницы входа
- **THEN** он перенаправляется на `/admin/login` и содержимое раздела не отдаётся

#### Scenario: Успешный вход

- **WHEN** администратор вводит верный пароль
- **THEN** открывается страница обзора `/admin`, и последующие запросы обслуживаются в этой сессии

#### Scenario: Неверный пароль

- **WHEN** администратор вводит неверный пароль
- **THEN** страница входа возвращается с сообщением об ошибке, а сессия не создаётся

#### Scenario: Изменение без CSRF-токена

- **WHEN** аутентифицированный клиент отправляет форму изменения без CSRF-токена
- **THEN** запрос отклоняется, данные не меняются

#### Scenario: Выход

- **WHEN** администратор нажимает выход
- **THEN** сессия завершается и следующий запрос к `/admin` снова требует входа

### Requirement: Каркас админки с навигацией по разделам

Система SHALL показывать в каждом разделе админки постоянное меню с переходами «Персоны», «Воспоминания», «Чаты», «Промпт», «Эмоции», «Настройки», «Модераторы» и MUST открывать «Настройки» по адресу `/admin`, не показывая отдельной страницы обзора.

#### Scenario: Обзор после входа

- **WHEN** администратор вошёл в админку
- **THEN** страница `/admin` показывает настройки и меню из семи разделов

#### Scenario: Переход в раздел

- **WHEN** администратор выбирает раздел в меню
- **THEN** открывается страница этого раздела, а меню остаётся доступным

### Requirement: Изменения из админки применяются без перезапуска

Система SHALL применять сохранённые в админке изменения к следующему запросу бота и MUST NOT требовать перезапуска процесса для промптов, алиасов, памяти, привязок и параметров модели.

#### Scenario: Правка промпта

- **WHEN** администратор сохранил новый промпт персоны
- **THEN** следующий ответ в привязанном чате строится по новому промпту без перезапуска

#### Scenario: Правка параметров модели

- **WHEN** администратор изменил модель или температуру
- **THEN** следующий запрос к модели использует новые значения

### Requirement: Модель выбирается из списка

Система SHALL предлагать модель в двух режимах, переключаемых радиокнопками «Прямой доступ» и «Провайдеры»: прямой — выпадающий список известных клиенту значений, сгруппированных по поставщику; провайдеры — три зависимых списка: провайдер, группа моделей, модель. Сохранение значения, которого нет в списке, MUST отклоняться ошибкой у поля модели. Наличие ключа MUST браться из `ai.provider_key_status`, а не из окружения админки.

#### Scenario: Выбор модели

- **WHEN** администратор открывает вкладку «Модель»
- **THEN** он видит радиокнопки режима, и в режиме «Прямой доступ» — список известных клиенту значений, сгруппированных по поставщику, с выбранной текущей моделью

#### Scenario: Значение вне списка

- **WHEN** в запросе пришло имя модели, которого нет в списке
- **THEN** форма возвращается с ошибкой у поля модели, а сохранённое значение не меняется

#### Scenario: Подсказка об отсутствии ключа

- **WHEN** администратор открывает выбор модели
- **THEN** у поставщика или агрегатора, у которого в `ai.provider_key_status` нет ключа, видна пометка с именем недостающей переменной окружения

### Requirement: Числовые параметры редактируются ползунком

Система SHALL показывать числовые параметры с известным диапазоном ползунком в границах допустимых значений и MUST по-прежнему проверять диапазон на сервере, отклоняя значение за границами.

#### Scenario: Ползунок показывает текущее значение

- **WHEN** администратор открывает карточку персоны на вкладке «Эмоции»
- **THEN** каждая эмоция и каждый числовой параметр показаны ползунком с текущим значением и границами диапазона

#### Scenario: Значение за границами

- **WHEN** в запросе пришло значение вне допустимого диапазона
- **THEN** форма возвращается с ошибкой у этого поля, а значение не сохраняется

#### Scenario: Ползунок показывает выбранное значение

- **WHEN** администратор двигает ползунок
- **THEN** рядом с ним сразу видно новое значение, ещё до сохранения формы

### Requirement: Подсказки к полям берутся из базы

Система SHALL показывать рядом с настраиваемым полем иконку с описанием и MUST брать текст из базы: `bot_settings.description` для настроек, `emotions.description` для эмоций, `persona_field_notes` для параметров персоны. Если описания нет, иконка MUST NOT выводиться.

#### Scenario: Описание у эмоции

- **WHEN** администратор открывает вкладку «Эмоции»
- **THEN** у каждого поля эмоции есть иконка с текстом из описания этой эмоции

#### Scenario: Описание у настройки

- **WHEN** администратор открывает вкладку «Модель»
- **THEN** у температуры есть иконка с текстом из описания этой настройки в базе

#### Scenario: Описание отсутствует

- **WHEN** у поля нет описания в базе
- **THEN** иконка у этого поля не выводится

#### Scenario: Правка описания в базе

- **WHEN** описание поля изменено в базе
- **THEN** следующий открытый раздел показывает новый текст без перезапуска бота

### Requirement: У чата без персоны один общий промпт

Система SHALL использовать настройку `aiPromtContext` как промпт любого чата без персоны, включая «синий» чат, и MUST NOT иметь отдельной настройки промпта для «синего» чата.

#### Scenario: Синий чат без персоны

- **WHEN** у «синего» чата нет привязанной персоны и в нём приходит запрос к AI
- **THEN** используется промпт из `aiPromtContext`

#### Scenario: Нет отдельного поля

- **WHEN** администратор открывает вкладку «Промты»
- **THEN** на ней есть только общий промпт чата без персоны, без поля для «синего» чата

### Requirement: Карточка персоны разделена на вкладки

Система SHALL показывать карточку персоны на двух вкладках — «Общее» (имя, промпт, алиасы) и «Эмоции» (эмоции и параметры) — и MUST сохранять карточку одной формой, возвращая ошибки на ту вкладку, где находится поле.

#### Scenario: Вкладка «Общее»

- **WHEN** администратор открывает карточку персоны
- **THEN** на вкладке «Общее» он видит имя, промпт и алиасы

#### Scenario: Эмоции в два столбца

- **WHEN** администратор открывает вкладку «Эмоции»
- **THEN** поля эмоций идут в два столбца, а параметры срыва, реплик и инициативы — ниже

#### Scenario: Ошибка возвращается на свою вкладку

- **WHEN** сохранение отклонено из-за эмоции вне диапазона
- **THEN** форма открывается на вкладке «Эмоции» с ошибкой у этого поля

#### Scenario: Ошибка в имени

- **WHEN** сохранение отклонено из-за пустого имени
- **THEN** форма открывается на вкладке «Общее» с ошибкой у поля имени

### Requirement: Примечание о живых данных

Система SHALL показывать в каждом разделе, где есть настройки, примечание о том, что правки применяются к следующему запросу без перезапуска.

#### Scenario: Раздел с настройками

- **WHEN** администратор открыл настройки или карточку персоны
- **THEN** он видит примечание, что админка работает с живыми данными и перезапуск не нужен

### Requirement: Список чатов разделён по наличию персоны

Система SHALL показывать в разделе «Чаты» сначала чаты с привязанной персоной, затем остальные, и MUST отделять группы заголовком.

#### Scenario: Чаты с персоной сверху

- **WHEN** администратор открывает «Чаты», и в базе есть чаты с персоной и без неё
- **THEN** сверху идёт группа «С персоной», ниже — «Без персоны»

#### Scenario: Все чаты с персоной

- **WHEN** у всех чатов есть привязанная персона
- **THEN** группа «Без персоны» не показывается

### Requirement: Раздел «Промпт» показывает шаблоны разделов

Система SHALL показывать страницу «Промпт» со списком разделов в порядке сборки, и у каждого раздела MUST быть поле шаблона со счётчиком символов рядом с бюджетом и кнопкой «вернуть по умолчанию»; для раздела персоны вместо поля MUST быть ссылка на карточку персоны, где правится её текст. Сохранённые шаблоны SHALL применяться со следующего запроса к AI без перезапуска.

#### Scenario: Список в порядке сборки

- **WHEN** администратор открывает страницу «Промпт»
- **THEN** разделы идут в том же порядке, в котором они собираются в промпт

#### Scenario: Сохранение шаблона

- **WHEN** администратор изменил шаблон раздела и сохранил
- **THEN** следующий ответ в чате строится по новому шаблону без перезапуска бота

#### Scenario: Возврат по умолчанию

- **WHEN** администратор нажал «вернуть по умолчанию» у раздела
- **THEN** в поле появляется исходный текст раздела, и он сохраняется как текущий

#### Scenario: Превышение бюджета

- **WHEN** длина шаблона превышает бюджет раздела
- **THEN** счётчик показывает превышение, а сохранение не блокируется

### Requirement: Предпросмотр собранного промпта

Система SHALL показывать предпросмотр промпта, собранного на реальных данных выбранного чата с тестовым вопросом, и MUST NOT изменять данные при предпросмотре. Пустые разделы в предпросмотре MUST отсутствовать так же, как в запросе к модели.

#### Scenario: Предпросмотр на чате с персоной

- **WHEN** администратор выбрал чат с персоной и нажал «предпросмотр»
- **THEN** он видит собранный промпт с разделами персоны, эмоций, памяти, людей и времени

#### Scenario: Предпросмотр в чате без персоны

- **WHEN** выбран чат без персоны
- **THEN** в предпросмотре нет разделов эмоций, обид и памяти, но есть техника, люди, время и формат ответа

#### Scenario: Предпросмотр ничего не меняет

- **WHEN** администратор открыл предпросмотр
- **THEN** история чата, память и настройки остаются прежними

### Requirement: Раздел «Эмоции» правит справочник и фразы

Система SHALL позволять править справочник эмоций — подпись, вес в агрессию, скорость затухания, базовое значение — и текст для каждой полосы значения. Раздел SHALL показывать шкалы вкладками, по одной на эмоцию, и одну вкладку за раз. Система MUST отклонять значения вне диапазонов: шкалы 0..10, вес от -1 до 1, затухание не меньше нуля. Изменения SHALL применяться со следующего ответа без перезапуска.

#### Scenario: Вкладка на каждую эмоцию

- **WHEN** администратор открывает раздел «Эмоции»
- **THEN** он видит по вкладке на каждую шкалу справочника в порядке вывода справочника, и открыта первая шкала

#### Scenario: Состав вкладки эмоции

- **WHEN** администратор открывает вкладку эмоции
- **THEN** он видит описание этой эмоции, четыре поля справочника и пять фраз по полосам значения 0-1, 2-4, 5-6, 7-8, 9-10 с подписью полосы, но не видит полей других эмоций

#### Scenario: Вкладка агрессии

- **WHEN** администратор открывает вкладку «Агрессия»
- **THEN** он видит пять фраз и пометку, что значение вычисляется из остальных эмоций и не редактируется, а полей справочника нет

#### Scenario: Новая эмоция в справочнике

- **WHEN** в справочник добавлена эмоция
- **THEN** в разделе появляется её вкладка без правки страницы

#### Scenario: Правка фразы полосы

- **WHEN** администратор изменил текст фразы для полосы 5-6
- **THEN** следующий ответ с эмоцией в этой полосе использует новый текст

#### Scenario: Правка веса эмоции

- **WHEN** администратор изменил вес эмоции в агрессию
- **THEN** уровень агрессии следующего ответа считается по новому весу

#### Scenario: Значение вне диапазона

- **WHEN** администратор ввёл вес 2 или базовое значение 11
- **THEN** форма показывает ошибку у поля и не сохраняет изменения

#### Scenario: Возврат на ту же вкладку

- **WHEN** администратор сохранил форму на вкладке эмоции
- **THEN** после сохранения снова открыта эта вкладка с подтверждением сохранения

#### Scenario: Ошибка открывает вкладку своей эмоции

- **WHEN** сохранение отклонено из-за значения на вкладке эмоции, которая не была открыта
- **THEN** форма открывается на вкладке этой эмоции с ошибкой у поля

### Requirement: Админка слушает loopback и VPN-подсеть

Система SHALL принимать HTTP-запросы админки на порту `BOT_ADMIN_PORT` (по умолчанию 8081) и MUST ограничивать доступ правилом файрвола: `127.0.0.1` и VPN-подсеть `10.8.0.0/24`, остальным адресам MUST отказывать. Публичного HTTPS-входа и домена MUST NOT быть.

#### Scenario: Запуск с настройками по умолчанию

- **WHEN** задан только `BOT_ADMIN_PASSWORD`
- **THEN** админка слушает `8081` на всех интерфейсах, доступна из `127.0.0.1` и из VPN-подсети и не принимает соединения из интернета

#### Scenario: Доступ из VPN-подсети

- **WHEN** запрос пришёл с адреса `10.8.0.0/24`
- **THEN** админка отдаёт страницу входа

#### Scenario: Запрос из интернета

- **WHEN** запрос пришёл с адреса вне `127.0.0.1` и VPN-подсети
- **THEN** соединение не устанавливается, содержимое админки не отдаётся

#### Scenario: Порт изменён

- **WHEN** задан `BOT_ADMIN_PORT` со свободным портом
- **THEN** админка слушает этот порт отдельным процессом, а AI-бот продолжает работать

### Requirement: Раздел настроек объясняет добавление ключей

Система SHALL показывать на странице настроек инструкцию по ключам провайдеров: где взять ключ, что деплой пересобирает `bot.env` из секретов репозитория, команды ручного добавления на сервере и таблицу переменных `BOT_AI_KEY_<ID>` с поставщиком, открываемыми моделями и пометкой о наличии ключа. Пометка MUST браться из `ai.provider_key_status`, а таблица — из каталога провайдеров.

#### Scenario: Таблица покрывает весь каталог

- **WHEN** администратор открывает страницу настроек
- **THEN** в таблице есть строка для каждого провайдера каталога со своей переменной `BOT_AI_KEY_<ID>`

#### Scenario: Ключ есть и ключа нет

- **WHEN** в `ai.provider_key_status` у части провайдеров записано наличие ключа
- **THEN** в строке такого провайдера стоит пометка «есть», а у остальных — «нет»

#### Scenario: Новый провайдер в каталоге

- **WHEN** в каталог добавлен провайдер
- **THEN** его строка появляется в таблице без правки шаблона страницы

#### Scenario: Сводка ключей видна до раскрытия инструкции

- **WHEN** администратор открывает страницу настроек
- **THEN** над формой есть строка со всеми поставщиками и пометкой «есть» или «нет» у каждого

#### Scenario: Метка ключа окрашена

- **WHEN** у провайдера ключ есть, а у другого нет
- **THEN** метка с ключом показана зелёной, а метка без ключа — красной

### Requirement: Настройки показывают текущую модель

Система SHALL показывать на странице настроек отдельным полем модель, которой бот отвечает сейчас, её поставщика и способ подключения — прямое или через агрегатор. Если сохранённой пары нет в каталоге, поле MUST вместо поставщика показывать предупреждение и модель по умолчанию, которой бот ответит.

#### Scenario: Прямое подключение

- **WHEN** сохранена модель прямого провайдера
- **THEN** поле показывает идентификатор модели, поставщика и «прямое подключение»

#### Scenario: Подключение через агрегатор

- **WHEN** сохранена модель агрегатора
- **THEN** поле показывает идентификатор, поставщика и «через агрегатор»

#### Scenario: Пара не найдена

- **WHEN** в настройках значение, которого нет в каталоге
- **THEN** поле показывает это значение и предупреждение, что бот ответит моделью по умолчанию

### Requirement: Провайдеры выбираются каскадом

Система SHALL показывать в режиме «Провайдеры» три списка, каждый следующий из которых появляется после выбора в предыдущем: провайдер, затем группа моделей этого провайдера, затем модель выбранной группы, и MUST NOT показывать в этом режиме плоский список моделей.

#### Scenario: Первый шаг каскада

- **WHEN** администратор выбрал режим «Провайдеры»
- **THEN** он видит список провайдеров, а списки групп и моделей появляются после выбора провайдера

#### Scenario: Группы зависят от провайдера

- **WHEN** администратор выбрал агрегатор AITunnel
- **THEN** в списке групп показаны только вендоры моделей этого агрегатора — DeepSeek, xAI, OpenAI, Google Gemini, Mistral

#### Scenario: Модели зависят от группы

- **WHEN** администратор выбрал группу «Google Gemini» у агрегатора AITunnel
- **THEN** в списке моделей показаны только модели этой группы

#### Scenario: Переключение режима скрывает чужие списки

- **WHEN** администратор переключил «Способ выбора модели»
- **THEN** списки другого режима исчезают из формы, а не остаются на месте выключенными

#### Scenario: Провайдер без ключа отмечен в списке

- **WHEN** в списке провайдеров у агрегатора нет ключа в окружении
- **THEN** его пункт содержит пометку «нет ключа», видимую без наведения на подсказку

### Requirement: Провайдер с единственной группой пропускает средний список

Если у провайдера все модели принадлежат одной группе, система SHALL NOT требовать выбора группы, показывая список моделей сразу после выбора провайдера.

#### Scenario: Одна группа у провайдера

- **WHEN** администратор выбрал агрегатор Abliteration, у которого все модели — одна группа
- **THEN** список моделей показывается сразу, без промежуточного выбора группы

#### Scenario: Несколько групп у провайдера

- **WHEN** у выбранного провайдера больше одной группы
- **THEN** каскад остаётся полным, и группа выбирается до модели

### Requirement: Режим и группа не хранятся отдельно

Система SHALL выводить режим из вида провайдера в `aiRoute`, а группу — из вендора выбранной модели, и MUST NOT хранить их как отдельные настройки. Сохранение формы SHALL записывать только пару «провайдер и модель».

#### Scenario: Возврат к сохранённой паре через агрегатор

- **WHEN** администратор открывает вкладку «Модель», а в настройках сохранена модель через агрегатор
- **THEN** форма открыта в режиме «Провайдеры», и провайдер, группа и модель уже выбраны

#### Scenario: Переключение режима без сохранения

- **WHEN** администратор переключил радиокнопку или список, но не сохранил форму
- **THEN** сохранённая пара не меняется, и повторное открытие вкладки показывает прежний выбор

#### Scenario: Прямая дверь записывает своего провайдера

- **WHEN** администратор сохранил модель в режиме «Прямой доступ»
- **THEN** в `aiRoute` записан прямой провайдер этой модели, и следующее открытие формы снова показывает режим «Прямой доступ»

### Requirement: Раздел «Эмоции» показывает потолок агрессии

Система SHALL показывать в разделе «Эмоции» сумму положительных весов справочника и вычисленный из неё потолок агрессии — округление вниз от `10 × сумма`, не выше 10 — и MUST считать их из текущего справочника, а не из константы.

#### Scenario: Сумма весов равна единице

- **WHEN** сумма положительных весов справочника равна 1.0
- **THEN** над вкладками указаны сумма 1.00 и потолок агрессии 10

#### Scenario: Сумма весов изменилась

- **WHEN** администратор изменил веса так, что сумма положительных стала 0.85
- **THEN** строка показывает сумму 0.85 и потолок агрессии 8, без ошибки сохранения

### Requirement: Настройки разделены на четыре вкладки

Система SHALL показывать настройки на четырёх вкладках — «Модель», «Память», «Промты», «Уведомления» — и MUST показывать одну вкладку за раз, возвращаясь на ту же вкладку после сохранения. Вкладки «Шаблоны» MUST NOT быть: шаблоны входа и выхода персоны удалены.

#### Scenario: Четыре вкладки

- **WHEN** администратор открывает страницу настроек
- **THEN** он видит вкладки «Модель», «Память», «Промты», «Уведомления», и открыта «Модель»

#### Scenario: Настройка на своей вкладке

- **WHEN** администратор открывает вкладку «Уведомления»
- **THEN** на ней показаны получатель уведомлений владельцу и флажок «Присылать обновления памяти», а параметры модели скрыты

#### Scenario: Возврат на ту же вкладку

- **WHEN** администратор сохранил форму на вкладке «Промты»
- **THEN** после сохранения снова открыта вкладка «Промты» с подтверждением сохранения

#### Scenario: Снятый флажок сохраняется выключенным

- **WHEN** администратор снял флажок «Присылать обновления памяти» и сохранил вкладку
- **THEN** настройка хранит выключенное значение, а после повторного открытия вкладки флажок снова снят

#### Scenario: Флажок включён по умолчанию

- **WHEN** настройка уведомлений о памяти ещё не заведена в базе
- **THEN** на вкладке «Уведомления» флажок показан включённым

### Requirement: Админка работает отдельным процессом

Система SHALL запускать админку отдельным jar и отдельным systemd-юнитом. Перезапуск или остановка админки MUST NOT прерывать опрос Telegram и ответы AI-бота, а перезапуск AI-бота MUST NOT делать страницы админки недоступными.

#### Scenario: Отдельный юнит

- **WHEN** на сервере запущены `telegram-bot.service` и `telegram-bot-admin.service`
- **THEN** это два разных процесса, и порт 8081 слушает только админка

#### Scenario: Рестарт админки

- **WHEN** выполняется `systemctl restart telegram-bot-admin`
- **THEN** страницы админки перезапускаются, а AI-бот продолжает отвечать в чатах

#### Scenario: Остановка админки

- **WHEN** админка остановлена
- **THEN** AI-бот продолжает отвечать, а привязки персон и память остаются доступными боту через базу

### Requirement: Админка не отправляет сообщения в чаты

Система SHALL NOT отправлять в чаты сообщения о входе и выходе персоны и MUST NOT запускать анализ памяти по кнопке. У админки нет бота, поэтому исходящих сообщений в Telegram нет вообще.

#### Scenario: Смена персоны

- **WHEN** администратор назначает, меняет или снимает персону
- **THEN** привязка сохраняется и история очищается по правилам памяти, но в Telegram ничего не отправляется

#### Scenario: Кнопки анализа нет

- **WHEN** администратор открывает раздел «Воспоминания»
- **THEN** кнопки ручного запуска анализа нет, а фоновый анализ выполняет AI-бот
