# Design

## Context

- `AiService` — синглтон-бин с `Map<Long, ChatMessages> chatHistory`; запись появляется лениво при первом сохранении (`AiService.java:60-62`), поэтому чат без сообщений в карте отсутствует, а `getChatHistorySize` (`AiService.java:65-66`) на нём падает с NPE.
- `ChatMessages` держит историю **по пользователям** (`Map<userId, UserMessages>`) и счётчик `numOfAiReset`; при чтении всё склеивается и сортируется по `System.currentTimeMillis()` — метки времени могут совпадать.
- `CommandDispatcher.dispatch` сохраняет любое не-командное сообщение и аргумент команды с префиксом `Сообщение от: @nick: <text>` (`CommandDispatcher.java:130-146`), то есть в истории лежит чат-лог, а не только обращения к `/ai`.
- `AI_ID = 0L` — синтетический идентификатор для system/assistant, такого пользователя в `tg_users` нет (важно при выборе внешних ключей).
- Параметры AI уже живут в `bot_settings` (`aiAnswerTemperature`, `maxTokensQuestion`), читаются через `SettingsService.getSettingValue`, который при ошибке возвращает `null`.
- Миграции — ручные идемпотентные SQL-скрипты в `migrations/`, накатываются `psql`; Flyway не используется.
- `tg_users.updated_at` существует, но `UPDATE` его не обновляет; в `tg_chats` колонки времени нет вообще.
- `ChatMessages` и `UserMessages` используются только внутри `AiService`.

## Goals / Non-Goals

**Goals:**

- История AI-чата и счётчик сбросов переживают перезапуск процесса.
- Окно истории ограничено настройкой, лимит считается на чат целиком.
- Системный промпт всегда актуален и не занимает место в окне.
- `/clear` и `/ai` работают на пустой истории без исключений.

**Non-Goals:**

- Горизонтальное масштабирование, распределённые блокировки, замена long polling на webhook.
- Перенос уже потерянной RAM-истории (её физически нет).
- UI подтверждения сброса — это #40; лимиты длины/модель — #41; `/summary` остаётся не подключённым.
- Ретенция по времени (TTL) — только по количеству сообщений.

## Decisions

### D1. Плоская таблица `ai_messages` на чат

```sql
CREATE TABLE IF NOT EXISTS public.ai_messages (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    chat_id bigint NOT NULL,
    role character varying(16) NOT NULL,
    content text NOT NULL,
    created_at timestamp with time zone NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS ai_messages_chat_id_idx ON public.ai_messages (chat_id, id);
```

Колонки `user_id` нет: автор уже зашит в `content` префиксом, а у system/assistant строк реального пользователя нет. Внешних ключей нет — `AI_ID = 0` не существует в `tg_users`.

*Альтернативы:* хранить по-пользовательские корзины как JSONB — отвергнуто, DeepSeek нужен один упорядоченный список, а текущий код и так склеивает и сортирует; отдельная колонка `user_id` — отвергнута как неиспользуемая.

### D2. Порядок задаётся `id`, а не временем

Identity монотонна и не зависит от часов; текущая сортировка по `System.currentTimeMillis()` даёт неопределённый порядок для сообщений одной миллисекунды. Чтение: `ORDER BY id DESC LIMIT ?`, затем разворот в памяти.

### D3. Промпт и счётчик сбросов не являются сообщениями

Системный промпт собирается при каждом запросе из `bot_settings` (`aiPromtContext` / `aiPromtMyChatContext`), счётчик хранится отдельно:

```sql
CREATE TABLE IF NOT EXISTS public.ai_chat_state (
    chat_id bigint PRIMARY KEY,
    resets integer NOT NULL DEFAULT 0
);
```

*Альтернатива:* продолжать хранить system-строки в истории, как сейчас. Отвергнута: копия промпта устаревает после смены настройки (spec требует актуальности), занимает окно и требует исключения из подсчёта при каждой обрезке, плюс лишняя копия PII в базе.

### D4. Обрезка при записи

После вставки сообщения одним запросом удаляется всё, что вышло за окно:

```sql
DELETE FROM ai_messages
WHERE chat_id = ?
  AND id NOT IN (SELECT id FROM ai_messages WHERE chat_id = ? ORDER BY id DESC LIMIT ?);
```

*Альтернатива:* обрезать при чтении — дешевле по записи, но таблица растёт без границы, что противоречит и приватности, и смыслу лимита.

### D5. Лимит читается при каждой записи

`aiHistorySize` берётся из `bot_settings` на каждой вставке через существующий `SettingsService`; при `null`, нечисловом или `<= 0` значении используется 100.

*Альтернатива:* прочитать один раз в конструкторе, как `answerTemperature` (`AiService.java:40`). Отвергнута: тогда смена настройки требует рестарта — ровно та болезнь, от которой избавляемся. Частота сообщений в боте делает лишний `SELECT` незаметным.

### D6. Один репозиторий вместо `ChatMessages`/`UserMessages`

Новый `AiChatRepository` в стиле существующих JDBC-репозиториев (`DataSource` + `PreparedStatement`) с методами: сохранить сообщение с обрезкой, получить последние N, посчитать сообщения, очистить чат, увеличить и прочитать счётчик сбросов. `ChatMessages` и `UserMessages` удаляются, вместо них `record AiMessage(String role, String content)` для сборки JSON в `AiService`.

Так `AiService` становится тонким: собрать `ArrayNode` = промпт + счётчик + сообщения из БД.

### D7. Ежедневное обновление пользователей и чатов — в SQL

Проверка «уже обновляли сегодня» переезжает в `WHERE`:

```sql
UPDATE tg_users SET ..., updated_at = now()
WHERE user_id = ? AND updated_at::date <> CURRENT_DATE;
```

В `tg_chats` добавляется `updated_at timestamp with time zone NOT NULL DEFAULT now()` (`ADD COLUMN IF NOT EXISTS`) и такая же проверка в `updateChatInDB`. Из `UserChatManager` удаляются `usersUpdateTime`/`chatsUpdateTime`; менеджер оставляет только проверку существования и вызов обновления, который в течение дня обновляет 0 строк.

*Альтернативы:* оставить карты как есть — отвергнуто, это ровно тот класс состояния, который задача убирает; upsert с `RETURNING` — отвергнуто как избыточное усложнение. Заодно исправляется двойной вызов `executeUpdate` в `UsersRepository.updateUserInDB`.

### D8. Политика отказа БД

Ошибка записи истории логируется, ответ пользователю не ломается — сообщение просто не попадёт в память. Ошибка чтения — запрос к AI уходит с одним системным промптом. Исключения не выходят в пул обработчиков `TelegramBot`.

### D9. Миграция `003_ai_history.sql`

Идемпотентно: две таблицы, индекс, `ADD COLUMN IF NOT EXISTS` для `tg_chats.updated_at`, `INSERT ... ON CONFLICT DO NOTHING` для `aiHistorySize = 100`.

## Risks / Trade-offs

- **История обнуляется на выкате** → принято осознанно: мигрировать нечего, в RAM её уже нет. Зафиксировано в proposal как BREAKING.
- **Окно в 100 сообщений короче сегодняшнего «помню всё»** → принято; это же требование #24. В активной группе это примерно сутки-двое переписки.
- **Переписка теперь постоянно лежит в БД** → ограничено окном; реальные сообщения и промпты не попадают в репозиторий и в seed-миграции, только в БД.
- **Параллельные сообщения одного чата** (кэшированный пул потоков в `TelegramBot`) → две вставки и две обрезки могут пересечься и срезать на одно сообщение больше. Для текущего трафика приемлемо; если станет заметно — advisory lock по `chat_id`.
- **Три запроса на сообщение** (настройка, вставка, обрезка) → приемлемо при текущей нагрузке; кэширование лимита сознательно не вводится (D5).
- **`/summary` по-прежнему не подключён** → вне scope, но после переноса в БД его реализация станет проще.

## Migration Plan

1. Накатить `migrations/003_ai_history.sql` на рабочую БД через `psql` **до** выката jar: новый код без таблиц не заработает.
2. Собрать jar, проверить запуск на заглушках (`BOT_TOKEN=1:dummy`, недоступный прокси) — контекст Spring и бин репозитория должны подняться.
3. Пуш в `main` → деплой перезапускает сервис; проверить в `journalctl`, что бот стартовал и Hikari подключился.
4. Проверка: `/ai` в чате, затем второй `/ai` — история должна сохраняться и после рестарта.
5. Откат: revert коммита; миграция аддитивная, старый код новые таблицы просто игнорирует.
