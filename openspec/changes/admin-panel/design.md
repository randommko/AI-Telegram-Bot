# Design

## Context

Приложение — один Spring Boot процесс без веб-слоя: бот работает long polling'ом через `BotLifecycle` (`SmartLifecycle`, фаза `Integer.MAX_VALUE - 100`), конфигурация приходит только из `BOT_*` env (`BotProperties`, `@Validated`), схема ставится вручную SQL-файлами от владельца схемы, а `app_user` получает права блоком `GRANT` в каждой миграции. Настройки читаются из `bot_settings` по месту, часть — на каждый запрос, часть зафиксирована в конструкторах (`AiService.answerTemperature`, `DeepSeekClient.maxTokens`, модель — константой `Settings.AI_MODEL`). `persona`, `persona_aliases`, `chat_personas`, `persona_memories`, `memory_categories`, `memory_people`, `memory_analysis_state` уже существуют (миграция 004). Тесты — юнит-уровня, `@SpringBootTest`/`@WebMvcTest` в проекте нет. `deploy.yml` на каждый пуш заново собирает `/etc/telegram-bot/bot.env` из GitHub Secrets и перезапускает сервис. Репозиторий публичный: промпты и пароли в git не попадают.

Мотивация — в `proposal.md`, требования — в `specs/`.

## Goals / Non-Goals

**Goals:**

- Веб-админка в том же jar и том же процессе, не мешающая long polling и остановке в бюджете `TimeoutStopSec=20`.
- Пять задач (#57–#61) как одна поставка: каркас, персоны, воспоминания, чаты, настройки.
- Параметры модели, лимитов и промптов читаются на каждый запрос, без рестарта — это закрывает #48 и #49.
- Админка выключена по умолчанию: без пароля её просто нет.

**Non-Goals:**

- HTTPS, внешний адрес, много пользователей и роли — доступ только через SSH-туннель к loopback.
- Настроение и обиды в ответах (#51), персоны в любых чатах (#62), внешние источники (#63).
- Миграция на webhook, горизонтальное масштабирование, кэш между экземплярами.

## Decisions

### 1. Один сервлет-коннектор на `127.0.0.1:8081`

`server.address=${BOT_ADMIN_BIND:127.0.0.1}` и `server.port=${BOT_ADMIN_PORT:8081}` в `application.properties` — Spring сам разрешает env-переменные в плейсхолдерах, Java-кода не нужно. Tomcat поднимается штатной авто-конфигурацией.

Альтернативы: второй `Connector` через `WebServerFactoryCustomizer` (лишняя деталь, у приложения нет других HTTP-потребителей) и `management.server.port` от actuator (тянет actuator, который не нужен).

### 2. Нет пароля — нет бинов, а не фильтр с 404

Все админские бины (контроллеры, security-конфигурация) помечены `@ConditionalOnProperty("bot.admin.password")`. Без переменной маршрутов `/admin/**` не существует, Spring отдаёт 404, а `ApplicationRunner` пишет один `WARN` при старте. Альтернатива — фильтр, возвращающий 404 на всё `/admin/**`, — требует, чтобы контроллеры всё равно существовали, и легко даёт утечку страницы при забытом фильтре.

`bot.admin.password` добавляется в `BotProperties` как опциональная вложенная запись (как `Proxy`): биндинг не ломает запуск без переменной.

### 3. Аутентификация: один пользователь в памяти, пароль из env

`InMemoryUserDetailsManager` с пользователем `admin` и `{bcrypt}`-хешем, посчитанным при старте из `BOT_ADMIN_PASSWORD`; кодировщик — `PasswordEncoderFactories.createDelegatingPasswordEncoder()`. Форма `/admin/login`, `logout` — POST, CSRF включён (Thymeleaf подставляет токен в формы), cookie сессии HttpOnly по умолчанию, `server.servlet.session.timeout=8h`.

Альтернативы: таблица пользователей в БД (не нужна — владелец один), `httpBasic` (пароль в браузере кэшируется и утекает в диалог заново).

### 4. Параметры модели — явные аргументы вызова, а не поля конструктора

`DeepSeekClient` перестаёт хранить `maxTokens` и константу модели: метод принимает модель, температуру и лимит токенов в параметрах запроса. `AiService` собирает их из `SettingsService` на каждый вызов. `AiMemoryExtractor` оставляет свою температуру 0.2 и лимит 2000, но модель берёт общую — смена модели действует и на анализ.

Разбор значений централизуется в `SettingsService.getInt(key, default)` / `getFloat(key, default)` с `WARN` и дефолтом при мусоре, вместо копий `try/catch` в `AiService`, `AiMemoryExtractor` и будущей админке.

Константа `Settings.AI_MODEL` переименовывается: ключ `aiModel` — новая константа `AI_MODEL_KEY`, значение по умолчанию — `DEFAULT_AI_MODEL = "deepseek-flash"`. Сейчас одно имя означает и ключ, и значение, и это первое, что запутает при чтении.

### 5. Мёртвые настройки удаляются, `aiPromtMyChatContext` остаётся

`aiSummaryTemperature` и `aiPromtSummaryContext` не читает никто: `Command.SUMMARY` объявлен, но обработчика в `handlers` нет. Уходят строки в `bot_settings` (миграция 005) и константы в `Settings`.

`aiPromtMyChatContext` НЕ удаляется: `PersonaService.resolvePrompt` использует его как запасной промпт, когда у привязной персоны пустой промпт. Это живой путь, а не мусор.

### 6. Админка переиспользует доменные репозитории

Никаких дублирующих SQL-слоёв: `PersonaRepository` получает выборку всех персон со счётчиками и чатами, вставку/обновление/удаление и работу с алиасами; `MemoryRepository` — постраничный поиск с фильтрами и CRUD; `SettingsService` — `listAll()` и `save(key, value, actor)`. Контроллеры в `org.example.Admin` вызывают их и валидаторы, шаблоны лежат в `templates/admin/`.

Альтернатива — отдельные `Admin*Repository` — размножила бы знание о таблицах и разошлась бы с ботом при следующей правке.

### 7. Проверка алиасов: глобальная уникальность в приложении, индекс в БД не меняем

Схема 004 сознательно разрешает одинаковые алиасы у персон в разных чатах (`persona_aliases_persona_alias_idx` по `(persona_id, lower(alias))`), и менять это в рамках админки незачем: бот ищет алиасы через привязку чата. Требование «уникален среди всех персон» проверяется запросом в валидаторе формы.

Запрещённые слова собираются из `Command.values()`: все алиасы без слэша, **кроме** имён-обращений команды `AI` (`юра`, `юрий`, `юрец`). Иначе карточку существующей персоны «Юра» нельзя было бы сохранить: её алиасы совпадают именно с этими синонимами. Формат алиаса — `[\p{L}\p{N}_]+`, одно слово.

### 8. Смена персоны: БД одной транзакцией, Telegram — после коммита

Порядок: `upsert` привязки, `DELETE` из `ai_messages` по чату, вставка сообщения о входе как `assistant` — одной транзакцией; затем отправка сообщений в Telegram. Ошибка Telegram логируется как `ERROR`, привязка остаётся (требование спеки). Отметка `memory_analysis_state` не трогается: `ai_messages.id` монотонны, поэтому новые сообщения всё равно новее отметки.

Счётчик `ai_chat_state.resets` не увеличивается: смена персоны — не пользовательский сброс памяти, и «тебе обнуляли память N раз» не должно расти от администратора. Настроение и обиды (`persona_state`, `persona_grudges`) **не** изменяются в этом изменении — см. открытые вопросы.

### 9. Ручной прогон анализа — синхронно, с результатом

`AiMemoryExtractor.analyzeChat` возвращает `AnalysisResult(messages, added, updated, deleted, rejectedDeletes)` вместо `void`; фоновый `analyzeDueChats` результат игнорирует, контроллер печатает его на странице. Вызов синхронный: клиент модели ограничен 60 секундами, а ответ нужен сразу — очередь и фоновые задания для одной кнопки были бы лишней машинерией. Страница предупреждает, что прогон может занять до минуты.

### 10. Пароль на прод — через GitHub-секрет, а не правкой `bot.env` по SSH

`deploy.yml` пересобирает `bot.env` на каждый пуш, поэтому вписанный по SSH пароль исчезнет при следующем деплое. Значение кладётся в секрет `BOT_ADMIN_PASSWORD`, в воркфлоу добавляется строка внутри блока `bot.env`. Пароль не попадает ни в репозиторий, ни в `design.md`, ни в логи.

Альтернатива — drop-in для systemd со вторым `EnvironmentFile` — пережила бы деплой, но создаёт второй источник правды о конфигурации; отклонено.

### 11. Миграция 005 — только данные

`migrations/005_admin_panel.sql`: `INSERT ... ON CONFLICT DO NOTHING` ключа `aiModel = deepseek-flash`, `DELETE` двух мёртвых ключей, блок прав для `app_user` как в 004 (на случай, если он отсутствовал). Схема не меняется, откат не нужен: удалённые ключи никем не читаются, а `aiModel` при отсутствии даёт дефолт из кода.

## Risks / Trade-offs

- **Tomcat в процессе бота меняет остановку.** `spring.lifecycle.timeout-per-shutdown-phase=10s` и `TimeoutStopSec=20` уже настроены; `server.shutdown=graceful` НЕ включаем, иначе Tomcat добавит свои 30 секунд и systemd убьёт процесс. → Оставить `immediate`, проверить `systemctl stop` на стенде.
- **Пароль бьётся о конфиг, если пустой.** `@ConditionalOnProperty` реагирует на пустую строку как на отсутствие — админка молча выключится. → В лог пишется явное `ADMIN disabled: BOT_ADMIN_PASSWORD не задан`.
- **`mvn test` не ловит wiring.** Добавление web-стартера меняет тип контекста; ошибка конфигурации проявится только на старте. → Обязательный бут-чек собранного jar на локальном PostgreSQL до пуша.
- **Первая страница за 60 секунд.** Ручной анализ держит HTTP-запрос всё время ответа модели. → Предупреждение на странице, таймаут клиента 60 с; повторное нажатие безопасно, потому что повторный прогон не создаёт дублей.
- **Валидация алиасов vs сиды.** Если набор запрещённых слов собрать из всех `Command` без исключения, правка персоны «Юра» станет невозможной. → Исключение имён-обращений закреплено тестом на реальных алиасах из миграции 004.
- **Правка промпта через веб — это PII на экране.** Промпты персоны и `bot_settings` содержат реальные имена. → Админка слушает только loopback, доступ по SSH-туннелю; в логи содержимое промптов не пишется.
- **Удаление мёртвых настроек необратимо.** Значения уйдут из прод-базы. → Удаляются только ключи с подтверждённым отсутствием читателей; `aiPromtMyChatContext` намеренно сохраняется.

## Migration Plan

1. Накатить `005_admin_panel.sql` на прод от владельца схемы **до** пуша: `app_user` получит `permission denied` на выборку `aiModel` иначе.
2. Создать GitHub-секрет `BOT_ADMIN_PASSWORD` (значение сообщается владельцу отдельно, в репозиторий не пишется), добавить строку в `deploy.yml`.
3. Пуш в `main` → сборка и перезапуск. Проверка: `journalctl -u telegram-bot` содержит старт бота и признак включённой админки.
4. Доступ: `ssh -L 8081:127.0.0.1:8081 <user>@<host>`, браузер на `http://127.0.0.1:8081/admin/login`.
5. Откат: снять `BOT_ADMIN_PASSWORD` из секрета и перезапустить — админка исчезает, бот продолжает работать; миграция отката не требует.

## Open Questions

- Судьба `persona_state` и `persona_grudges` при смене персоны: очищать вместе с историей или оставлять? В этом изменении состояние не трогается; вопрос вынесен отдельно и ответ на него спеку не меняет.
- Формат отчёта ручного прогона: числа на странице (текущий выбор) или отдельная страница с журналом прогонов. Оба варианта укладываются в требования спеки.
- Очищать ли `ai_messages` при снятии персоны (чат без персоны). Задача #60 этого не требует; поведение намеренно не специфицировано, пока не решено.
