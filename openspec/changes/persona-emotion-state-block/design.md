# Design

## Context

См. `proposal.md` — Why. Что задаёт форму решения:

- Карточка персоны (`AdminPersonaController`, `persona-form.html`) показывает только характер: базовые значения шкал из `config.emotions` на вкладке «Эмоции».
- Действующее состояние считает `EmotionService.stateFor(personaId, readOnly)`: затухание к характеру, фраза полосы по значению, вычисляемая агрессия. Тем же вызовом пользуется бот (`AiService`) и план (`PromptComposer.composeForPlan`).
- `EmotionService.blockFor` не годится как «готовый блок»: заголовок он берёт из константы `PromptDefaults.EMOTIONS_HEADER`, а бот — из настройки `aiPromptEmotionsHeader`, которую правят на странице «Промпт». Обрамление `## Твоё состояние сейчас` добавляет `PromptComposer.render`, а не `blockFor`.
- `stateFor(id)` без флага чтения вызывает `ensureForPersona` — `INSERT ... ON CONFLICT DO NOTHING`. Для GET-страницы это запись в базу.
- `stateFor` отдаёт строки в порядке `emotion_code`, а справочник — по `sort_order`.
- Админка уже зависит от ядра и от `PromptComposer` (`AdminPromptController`), новых бинов и модулей не нужно.

## Goals / Non-Goals

**Goals:**

- Обе части блока считаются одним чтением состояния, поэтому таблица и текст промпта не могут разойтись.
- Сборка раздела промпта для показа и для ответа — один код.
- Открытие карточки ничего не пишет в базу.
- Текст системного промпта, который получает модель, не меняется.

**Non-Goals:**

- Показ всего системного промпта: он остаётся в предпросмотре промпта.
- Автообновление страницы, графики, история настроения, правка эмоций из блока.
- Новые настройки, эндпоинты и миграции.

## Decisions

### D1. Две части в одном блоке

Таблица отвечает на вопрос «что у персонажа сейчас» и показывает все шкалы справочника, включая вычисляемую агрессию: подпись, «характер», «сейчас», фразу полосы. Раздел промпта отвечает на вопрос «что модель прочитает дословно» и показывается отдельным `<pre>` под таблицей.

Колонка «характер» нужна, потому что отбор в промпт сравнивает «сейчас» с характером: без неё не объяснить, почему эмоция не попала в раздел.

Альтернатива «одна таблица с пометкой „в промпте“» отклонена: она не показывает, что модель читает на самом деле, и требует открывать предпросмотр. Альтернатива «отдельная страница состояния» отклонена: ради одного раздела модератору пришлось бы уходить из карточки.

### D2. Сборка раздела — один метод сборщика промпта

В `PromptComposer` появляется приватный `emotionsBody(String)` — он принимает готовые строки состояния от `EmotionService` и добавляет заголовок из настроек либо оставляет строку о ровном состоянии, — и публичный `emotionsSection(EmotionState)`, который получает тело через `EmotionService.bodyText(state)` и прогоняет его через тот же `render(...)`, что и `compose()`. `compose()` и `composeForPlan()` берут тело из `emotionsBody`, поэтому показ и ответ используют один код.

Почему не `EmotionService.blockFor`: он подставляет константу вместо настройки и не содержит обрамления — «готовый блок» врал бы после первой правки заголовка в админке.

Почему не склейка в шаблоне или контроллере: заголовок раздела, обрамление и правило ровного состояния — три места, где текст разойдётся с промптом при первой же правке.

Публичный метод принимает уже посчитанное состояние, а не id персоны: контроллер делает одно чтение на страницу, а не два. Два чтения дали бы шанс разойтись на границе затухания, когда целое значение меняется между запросами.

### D3. Только чтение, без добивки строк

Контроллер вызывает `stateFor(id, true)` — тот же режим, что у предпросмотра промпта. `ensureForPersona` не запускается, и открытие карточки не меняет данные.

Следствие: у персоны без сохранённых значений эмоций состояние выйдет «ровным», хотя бот после своей добивки посчитает иначе. В этом случае блок не показывает ни таблицу значений, ни раздел промпта, а сообщает, что сохранённых значений ещё нет и их создаст сохранение карточки. Ошибка чтения (`stateFor` вернул `null`) показывается отдельным сообщением — пустая таблица и ложное «ровное состояние» запрещены сценариями спеки.

### D4. Порядок строк — как в справочнике

`stateFor` возвращает строки по коду эмоции. Контроллер собирает строки таблицы в порядке `findCatalog()` (он уже лежит в модели для вкладки «Эмоции»), подставляя значение по коду, и добавляет агрессию последней — она производная и строки у персоны не имеет. Шаблон остаётся без сортировки и поиска по коду.

### D5. Блок над вкладками, вне формы

`persona-form.html`: секция сразу над `<nav class="tabs">`, до `<form class="setting">`. Условие показа — `form.id != null`; проверки `editable` нет, потому что смотреть состояние вправе любой, кому доступна карточка. Оформление — существующие `table.list`, классы `.hint` и `<pre>` как на странице предпросмотра промпта; новых стилей не нужно.

Значения пересчитываются при каждой загрузке, поэтому в заголовке блока печатается время расчёта: иначе модератор примет затухание за случайные скачки.

## Risks / Trade-offs

- **Лишние запросы на открытие карточки** (справочник, фразы, значения персоны) → это три чтения по индексам на страницу, которая и так читает персону и справочник; кеш не вводим, иначе блок начнёт показывать устаревшее состояние.
- **Значения меняются между перезагрузками** → в блоке печатается время расчёта и подпись, что значение затухает к характеру.
- **Длинные фразы полос** → таблица на существующем `table.list` переносит текст; отдельного усечения не делаем, чтобы фраза читалась целиком.
- **Расширение публичного API ядра** → добавлен один метод, принимающий готовое состояние; логика промпта не двигалась.
- **Персона без сохранённых значений** → вместо состояния показывается предупреждение; сохранение карточки создаёт строки штатным путём.

## Migration Plan

Схема базы не меняется, миграций нет. Деплой затрагивает `core/**` и `admin/**`, поэтому выкатывается админка; бот перезапускается только если деплой bot сработает по фильтру путей, а текст его промпта не меняется. Откат — revert коммита: блок исчезает, промпт остаётся прежним.
