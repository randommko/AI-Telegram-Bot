# Design

## Context

См. `proposal.md`. Существенное для подхода:

- Админка — Thymeleaf-шаблоны в одном процессе, один администратор, без JS-фреймворка: в `layout.html` лежит весь CSS, скриптов нет.
- `AdminSettingsController` держит статический список групп (`FORM`) и рендерит одну форму; значения полей — строки, проверка в `AdminSettingsValidator`.
- Карточка персоны — одна форма `PersonaForm` (record) с картой значений эмоций; ошибки адресуются ключом поля (`emotion.гнев`).
- `PersonaService.resolvePrompt` выбирает: промпт персоны → `aiPromtMyChatContext` для «синего» чата → `aiPromtContext` → константа в коде.
- Описания уже частично живут в базе: `bot_settings.description` (у части ключей) и `emotions.description` (у всех эмоций).

## Goals / Non-Goals

**Goals:**

- Структура, в которой видно, что где настраивается, и рядом с каждым полем — объяснение.
- Один общий промпт чата без персоны вместо двух параллельных настроек.
- Минимум новых сущностей: одна таблица описаний для полей, у которых описания нет.

**Non-Goals:**

- Перенос воспоминаний в карточку персоны — отдельное изменение.
- Удаление промпта анализа переписки — отдельная задача (пункт 7 #66).
- Любые изменения в том, как бот отвечает.
- Редактирование описаний полей из админки — тексты пока правятся в базе.

## Decisions

### Вкладки — на сервере, без JS

Вкладка — это параметр `?tab=`, а не клиентский переключатель: каждая вкладка — отдельный GET, форма шлёт скрытое поле с текущей вкладкой, после сохранения редирект возвращает на неё. Причина: без JS, и после ошибки валидации нужно знать, какую вкладку открыть (ошибка может быть в поле другой вкладки — тогда открывается вкладка с первой ошибкой).

Альтернатива «все вкладки в одном DOM, скрыты CSS» отклонена: тогда при ошибке на другой вкладке её содержимое уже отрисовано, но пользователь её не видит.

### Пять вкладок вместо трёх

Пункт 8 просит три, но групп пять. «Память» отделяется от «Модели», потому что это про то, сколько памяти идёт в промпт и как часто её обновлять, а «Уведомления» — единственная настройка, не относящаяся ни к модели, ни к промптам. Пользователь выбрал пять.

### Один общий промпт, `aiPromtMyChatContext` удаляется

`aiPromtContext` становится промптом любого чата без персоны. Ветка выбора в `PersonaService` упрощается до «персона → `aiPromtContext` → константа». Строка `aiPromtMyChatContext` в базе удаляется миграцией: её значение содержит реальный промпт «синего» чата, и удаление необратимо — перед накатом пользователь копирует текст, если он ему нужен.

**BREAKING** для случая «синий чат без персоны»: раньше он брал отдельный промпт, теперь общий. На проде персона привязана, поэтому поведение не меняется, пока привязку не снимут.

### Список моделей — константа в коде

Клиент умеет только DeepSeek, поэтому список — защита от опечатки, а не каталог провайдеров: `deepseek-chat`, `deepseek-flash`. Значение `aiModel` остаётся строкой в `bot_settings`, проверяется при сохранении. Альтернатива «список в настройке» отклонена: список меняется вместе с кодом клиента, а не с данными.

### Ползунки остаются полями формы

`input type=range` отправляет строку, как и текстовое поле, поэтому `PersonaForm` и `PersonaForm`-валидатор не меняются: серверная проверка диапазона сохраняется. У диапазонов с шагом (температура 0..2 шаг 0.1, токены) рядом с ползунком остаётся поле ввода, чтобы можно было вписать точное значение.

### Описания — рядом с сущностью, три источника

- настройки: `bot_settings.description`, недостающие описания заполняются миграцией;
- эмоции: `emotions.description` (уже заполнено и уже выводится);
- параметры персоны: новая таблица `persona_field_notes(field_key primary key, note text)` на шесть строк.

Одна общая таблица отклонена: описания эмоций пришлось бы продублировать из справочника. Правило простое и объяснимое: описание живёт там же, где данные, которые оно описывает.

### Иконка (i) без JS

Всплывашка — `title` у иконки плюс CSS-тултип на `:hover`/`:focus`. Никаких скриптов: их в админке нет и заводить ради подсказки не стоит. Иконка появляется только если текст непустой.

### Полоса «живые данные» — во фрагменте layout

Примечание выводится фрагментом в шаблоне и подключается в разделах с настройками (настройки, карточка персоны). Список персон и чаты его не получают: там действия, а не параметры.

## Risks / Trade-offs

- [Удаление `aiPromtMyChatContext` необратимо] → в задачах отдельный пункт: пользователь копирует текст промпта себе до наката миграции.
- [Вкладки на `?tab=` ломают закладки на конкретную настройку] → это осознанно: адрес вкладки стабилен (`?tab=prompts`), а не якорь.
- [Ползунок с шагом 0.1 для температуры даёт дробные значения] → значение по-прежнему проверяется валидатором на 0..2, формат хранения не меняется.
- [Описания в трёх местах] → правило зафиксировано в спеке и в этом документе; новая таблица нужна только там, где описаний не было.
- [Пять вкладок расходятся с пунктом 8 issue] → решение пользователя от 2026-11-03, отмечено в issue комментарием.

## Migration Plan

1. `migrations/008_admin_ui.sql`, идемпотентная: `CREATE TABLE IF NOT EXISTS persona_field_notes`, `INSERT ... ON CONFLICT DO NOTHING` для шести заметок, `UPDATE bot_settings SET description = ...` там, где пусто, `DELETE FROM bot_settings WHERE setting_key = 'aiPromtMyChatContext'`.
2. Перед накатом — скопировать значение `aiPromtMyChatContext` из прода, если оно ещё нужно.
3. Накат руками от владельца схемы, затем пуш (деплой перезапускает бота).
4. Проверка: `/admin` открывает настройки, вкладки переключаются, у эмоций видны описания, модель выбирается из списка, в карточке персоны есть вкладки.

Откат: восстановление строки `aiPromtMyChatContext` из копии и предыдущий jar; таблица заметок безвредна и остаётся.
