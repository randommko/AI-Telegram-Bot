# Design

## Context

См. `proposal.md` — Why. Ограничения, которые задают форму решения:

- Карточка персоны (`/admin/personas/{id}`) — один `<form POST /admin/personas>`: вкладки «Общее» и «Эмоции» это секции одной формы, неактивная скрыта классом `hidden`.
- Воспоминания обслуживает отдельный `AdminMemoryController` с семью маршрутами, своим `MemoryFilter` (`personaId` nullable) и `PAGE_SIZE = 25`.
- В HTML нет вложенных форм, поэтому список памяти с фильтром и строками «Править/Удалить» не может жить внутри формы персоны.
- Память видна только тем, кто вправе править персону: `AdminAccess.visiblePersonaIds()` → `PersonaRepository.editablePersonaIds()` (авторство или выдача).

## Goals / Non-Goals

**Goals:**

- Одна точка входа в память — вкладка карточки; список ограничен персоной из пути.
- Сохранить существующие страницы формы и подтверждения удаления, поменяв только адреса и возврат.
- Убрать старую страницу и пункт меню, не сломав старые ссылки.
- Показать названия чатов в списке персон.

**Non-Goals:**

- Расширение доступа к памяти на просмотр по выданному чату.
- Ручной прогон анализа, любые изменения бота и схемы базы.
- Настройки, эмоции, модераторы и вход — изменение `admin-ui-polish`.

## Decisions

### D1. Вкладка — состояние страницы, а память вне формы персоны

Навигация вкладок выносится из `<form>` персоны. На «Общее» и «Эмоции» рендерится форма персоны, на «Воспоминания» — форма фильтра и таблица со своими формами строк.

Альтернатива «оставить всё одной формой» невозможна из-за запрета вложенных форм. Альтернатива «отдельный POST для памяти внутри формы персоны» дала бы одну кнопку «Сохранить» на два разных объекта и смешала бы валидацию.

### D2. Маршруты памяти вложены в карточку

```
GET  /admin/personas/{id}?tab=memories&category=&personId=&q=&coreOnly=&deleted=&sort=&page=
GET  /admin/personas/{id}/memories/new
GET  /admin/personas/{id}/memories/{memoryId}
POST /admin/personas/{id}/memories
GET  /admin/personas/{id}/memories/{memoryId}/delete
POST /admin/personas/{id}/memories/{memoryId}/delete
POST /admin/personas/{id}/memories/{memoryId}/restore
```

Персона берётся из пути и является единственным источником истины. `MemoryForm` продолжает нести `personaId` скрытым полем для валидатора, но контроллер сравнивает его с путём и при расхождении не сохраняет.

Альтернатива — оставить `/admin/memories/...` и передавать персону параметром: два владельца одного значения и риск записать память не той персоне. Альтернатива с `returnUrl` в форме отклонена из-за открытого редиректа.

### D3. Видимость вкладки повторяет правило правки

Вкладка рендерится только при `access.canEditPersona(id)`; сами маршруты памяти проверяют то же право. `visiblePersonaIds()` и `editablePersonaIds()` не меняются.

Альтернатива «показывать всем, кто видит карточку» расширяет доступ к фактам о людях чата и отклонена.

### D4. Старый адрес редиректит, страница удаляется

`GET /admin/memories` отвечает редиректом: при `personaId`, который пользователь вправе править, — на `/admin/personas/{id}?tab=memories`; иначе — на `/admin/personas`. Остальные маршруты `/admin/memories/**` удаляются вместе с шаблоном списка как самостоятельной страницей. Пункт «Воспоминания» убирается из меню и владельца, и модератора; у модератора остаются «Персоны» и «Чаты».

Альтернатива «404» ломает закладки; альтернатива «оставить список по всем персонам» дублирует таблицу и разъезжается с вкладкой.

### D5. Форма и подтверждение остаются отдельными страницами

`memory-form.html` и `memory-delete.html` переиспользуются: меняются `th:action`, скрытый `personaId` и ссылки «Отмена/Назад» на вкладку. Список остаётся единственным, что живёт в карточке.

Встроить форму в вкладку нельзя: она оказалась бы внутри формы фильтра. Кроме того, ошибки валидации должны сохранять введённые значения, а это проще на отдельной странице.

### D6. Фильтры — параметры адреса карточки

Вкладка читает те же параметры, что раньше читал список, кроме `personaId`. Ссылки пагинации собираются из текущего `MemoryFilter`, поэтому `deleted`, `coreOnly` и сортировка не теряются. «Применить» ведёт на тот же адрес с `tab=memories`.

### D7. Названия чатов вместо идентификаторов

`PersonaSummary.chats` остаётся строкой для вывода. SQL в `findAllWithCounts` меняет сборку:

```sql
COALESCE(NULLIF(btrim(c.chat_title), ''), cp.chat_id::text)
```

с `LEFT JOIN shared.tg_chats c ON c.chat_id = cp.chat_id`. Идентификатор остаётся запасным вариантом для чата без названия.

Альтернатива — вернуть список объектов «чат и название» — меняет тип в `core` ради одного столбца; не нужно, пока `chats` никто, кроме `personas.html`, не читает.

### D8. Пустая память и сообщения

Пустой список показывает подсказку «Памяти пока нет — добавьте первую запись», а не пустую таблицу. Сообщения `saved`/`error` выводятся на вкладке после редиректа.

## Risks / Trade-offs

- **Ошибка сохранения памяти теряет ввод** → форма при ошибке рендерится заново с `MemoryForm` и списком людей, как сейчас; на вкладку не редиректим.
- **Память персоны A через адрес персоны B** → персона из пути сверяется с `details.personaId()`; при расхождении запись не меняется и показывается ошибка.
- **Пагинация теряет фильтр «удалённые»** → ссылки строятся из `MemoryFilter`, а не из ручного набора параметров.
- **Старые закладки модератора** → редирект на список персон, потому что чужую память он не правит.
- **Столбец «Чаты» стал длиннее названий** → названия выводятся как есть через запятую; при необходимости CSS переносит строку, ширина таблицы не фиксирована.
- **Две вкладки у модератора против трёх у владельца** → это осознанное правило, тест фиксирует обе ветки.

## Migration Plan

Схема базы не меняется, миграции нет. Деплой затрагивает `admin/**` и `core/**`, поэтому запускается `Deploy admin`; бот продолжает работать на прежней сборке. Откат — revert коммита, данные не затрагиваются.
