# Design

## Context

См. `proposal.md`. Существенное для подхода:

- `migrations/004_personas_and_memories.sql` уже создал `personas.base_joy/base_anger/base_offence/base_fatigue/base_sarcasm`, параметры эмоциональности и таблицу `persona_state` (ключ `chat_id`). Ни одна строка Java `persona_state` не читает — таблица пустая и мёртвая.
- Эмоции в промпт не попадают вообще: `AiService.getHistoryInChat` собирает системный промпт, блок памяти и историю.
- Промпт персоны читается из `personas.prompt` на каждый запрос; в нём уже описаны черты характера прозой.
- База — общая prod-инстанция PostgreSQL; миграции накатываются вручную от владельца схемы, бот ходит под `app_user`.
- Модель — `deepseek-flash`, reasoning-модель: любое удлинение входа бьёт по латентности и лимиту токенов.

## Goals / Non-Goals

**Goals:**

- Одна модель эмоций, которая переживёт #51 (план, обиды, срыв) без переделки схемы.
- Настроение видно в ответах уже этим изменением: блок в промпте собирается из БД.
- Характер и настроение разделены, у затухания есть точка, к которой тянуться.
- Админка перестаёт знать про пять шкал: поля строятся по справочнику.

**Non-Goals:**

- Сдвиги эмоций от сообщений, шаг «план», обиды, срыв, мультиреплики, поиск по теме, инициатива — issue #51.
- Редактирование фраз шкал из админки: в этом изменении они создаются миграцией.
- Персона в чатах без привязки — issue #62.

## Decisions

### Состояние принадлежит персоне, а не чату

Ключ — `persona_id`. Ключ `(persona_id, chat_id)` отклонён: он требует второй таблицы под состояние и превращает «сброс при смене персоны» в код. При ключе по персоне смена персоны в чате решает задачу сама — новая персона читает свою строку, а не чужую. Цена: когда #62 разрешит персону в нескольких чатах, настроение станет общим на все её чаты. Это принимается как «один непрерывный характер», и строку в #51 про «у каждого чата своё состояние» надо заменить.

Следствие, которое надо держать в голове: обиды (`persona_grudges`) остаются с ключом чата — злость может прийти в чат, где повода не было. В блоке состояния это подаётся как настроение вообще, без адресата.

### Характер и настроение в одной таблице

`persona_emotions(persona_id, emotion_code, base_value, value, updated_at)`. Альтернатива «только `value`, характер в промпте» отклонена: тогда после суток все персоны нейтральны и настраивать характер числами нельзя. Альтернатива «две таблицы» отклонена как лишний join без выгоды.

`value` — значение **на момент `updated_at`**, действующее считается при чтении. Это убирает запись из пути чтения: затухание — чистая функция от времени, `updated_at` двигают только реальные изменения (админка сейчас, план в #51).

### Агрессия — вычисляемый индекс

В справочнике у эмоции есть `aggression_weight` (может быть нулевым или отрицательным). Агрессия = `clamp(Σ weight × value, 0, 10)`, нигде не хранится. Альтернатива «двенадцатая редактируемая шкала» отклонена: инвариант «не максимум агрессии при максимуме радости» пришлось бы проверять после каждой записи в трёх местах, а модель в #51 всё равно могла бы вернуть противоречивый набор.

Инвариант добивается двумя механизмами: отрицательный вес радости в сумме и жёсткое правило `если радость ≥ 7 → агрессия ≤ 10 − радость`.

Умолчания весов (правятся в БД): гнев +0.55, брезгливость +0.20, сарказм +0.15, зависть +0.10, радость −0.25, ностальгия −0.10; печаль, тревожность, стыд, хандра, страх — 0.

### Фразы полосами, а не по каждому значению

`emotion_phrases(emotion_code, from_value, to_value, phrase)`, полосы 0-1, 2-4, 5-6, 7-8, 9-10. Альтернатива «фраза на каждое значение» (132 строки) отклонена: фраза — это инструкция «как отвечать», одиннадцать её версий различались бы одним словом. Полосы совпадают с тем, как описана шкала агрессии в задаче.

### Блок состояния селективный

В промпт идут эмоции с отклонением от базы ≥ 2, всегда агрессия, максимум четыре — по величине отклонения. Иначе блок из одиннадцати фраз превращается в шум, который модель перестаёт читать, и удлиняет вход reasoning-модели на каждом запросе. Спокойная персона получает одну строку.

Блок помечается как текущее состояние; характер остаётся в `personas.prompt`. Без этой пометки состояние спорит с промптом («язвительный, злой» против «радость 8: добродушен»), и модель выбирает непредсказуемо.

### Производная шкала не имеет значения у персоны

Агрессия есть в справочнике (`is_derived = true`) и в таблице фраз, но строки в `persona_emotions` у неё нет: её значение вычисляется. Все остальные эмоции справочника — редактируемые, у них есть `base_value` и `value`.

### Компоненты

- `EmotionRepository` — справочник, фразы, значения персоны; чтение и запись `base_value`/`value`.
- `EmotionService` — действующие значения (затухание), агрессия, выбор фразы по полосе, текст блока.
- `AiService` — блок добавляется системным сообщением рядом с блоком памяти, как уже сделано в `addMemories`; ошибки чтения эмоций логируются и не ломают ответ.
- Админка: `PersonaForm` получает список значений по эмоциям вместо пяти строковых полей, `AdminPersonaValidator` строит ошибки по коду эмоции («Злость» и диапазон берутся из справочника), шаблон рисует таблицу полей.

## Risks / Trade-offs

- [Промпт удлиняется на каждом запросе] → блок ограничен четырьмя фразами; при первом прогоне смотреть `prompt_tokens` в логе пустого ответа.
- [Затухание на чтение даёт «прыжок» между двумя сообщениями] → затухание линейное по часам и детерминированное; при желании сглаживается в #51, когда появятся сдвиги.
- [Справочник правится в БД без валидации] → CHECK на диапазоны, вес в −1..1, при некорректной строке — предупреждение в лог и значение по умолчанию.
- [Форма с 12 полями ломает существующие тесты валидатора] → ошибки адресуются кодом эмоции, тесты переписываются на справочник.
- [Удаление `base_*` несовместимо со старым jar] → откат только вместе с дампом и предыдущим jar, не «просто откатить деплой».
- [Персона без строк в `persona_emotions`] (создана старым кодом или вручную) → значения создаются лениво из умолчаний справочника при первом чтении.

## Migration Plan

1. `migrations/006_persona_emotions.sql`, идемпотентная, от владельца схемы: `CREATE TABLE IF NOT EXISTS emotions`, `emotion_phrases`, `persona_emotions`; `INSERT ... ON CONFLICT DO NOTHING` для справочника и ~60 фраз.
2. Перенос значений существующих персон одним `INSERT ... SELECT`: радость ← `base_joy`, гнев ← `base_anger`, хандра ← `base_fatigue`, сарказм ← `base_sarcasm`; остальные — из `base_default` справочника; `value = base_value`. `base_offence` никуда не переносится: эмоции «обида» в новой модели нет, обиды на людей живут в `persona_grudges` (#51) и там пусто.
3. `DROP TABLE IF EXISTS persona_state`; `ALTER TABLE personas DROP COLUMN IF EXISTS base_*`, `offence_decay_per_hour`; переименование `anger_threshold` → `aggression_threshold` через `DO`-блок с проверкой `information_schema` (повторный накат не должен падать).
4. Гранты `app_user` на новые таблицы — как в 004, включая `ALTER DEFAULT PRIVILEGES`.
5. Перед пушем: дамп `personas`, `persona_state`, `persona_grudges`; накат миграции руками на прод; локальный бот-чек собранного jar; пуш в `main` (деплой перезапускает бота).

Откат: восстановление из дампа + предыдущий jar. Миграция необратима по своей природе (`DROP COLUMN`), поэтому дамп — обязательный шаг, а не страховка.

## Open Questions

- Тексты ~60 фраз и подписи эмоций пишутся при реализации; на архитектуру не влияют.
- Экран редактирования фраз шкал из админки — отдельное изменение, если понадобится.
- Подписи полюсов («плюс / минус / стиль») в админке — косметика, решается при вёрстке.
