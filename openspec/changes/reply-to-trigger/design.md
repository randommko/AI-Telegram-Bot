# Design

## Context

`CommandDispatcher` — единственное место, где есть исходное `Message`: идентификатор, автор и тип чата. Дальше `AiService` работает только с `chatId`, а автора берёт из `repository.findLastMessages(chatId, 1)`. Апдейты обрабатываются в `Executors.newCachedThreadPool`, поэтому «последнее сообщение в базе» может принадлежать другому человеку.

## Approach

1. `CommandDispatcher` передаёт в `AiService` идентификатор сообщения (только для групп) и `MessageAuthor.from(message.getFrom())`.
2. `AiService` больше не читает автора из истории; `currentAuthor()` удаляется, обида и эмоции применяются к переданному автору.
3. `MessageSender` получает необязательный `replyToMessageId`:
   - `sendMessage(chatId, text, replyId)` — реплай с откатом на обычную отправку;
   - `sendLongMessage(chatId, text, replyId)` — реплай только у первой части.
4. `sendReplyMessage` удаляется: у него нет вызовов, а откат нужен всем реплаям.
5. Уведомление о недоступности модели отправляется тем же методом с тем же `replyId`.

## Decisions

- **Реплай только в группах.** В личке цитата — шум: собеседник и так один. Решение зафиксировано в задаче как уточняемое.
- **Откат на любую ошибку реплая, а не только на «message to be replied not found».** Различать коды дороже, чем повторить отправку; риск дубля есть только если Telegram выполнил запрос, но не вернул ответ, — это реже, чем удалённый триггер.
- **Автор в план не передаётся.** План его не читает; получатель последствий — `AiService`. Разметка «сейчас пишет» в разделе «Люди» по-прежнему считается по истории — это чинится в задаче про факты об участниках (#88), где раздел переделывается.

## Risks

- Двойная отправка при потере ответа Telegram после успешного реплая. Приемлемо: текст короткий, а потеря ответа хуже дубля.
- Тесты диспетчера мокают `Chat` без типа: в них нужно явно включить группу, иначе реплай не появится.
