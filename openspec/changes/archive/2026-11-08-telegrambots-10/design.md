# Design

## Context

Сейчас бот и core зависят от агрегатного артефакта `org.telegram:telegrambots` 6.5.0. Эта линия закрыта версией 6.9.7.1 (февраль 2024); начиная с 7.0.0 библиотека разрезана на модули, а точка входа long polling переписана. Spring Boot 3.5, Java 17, 477 тестов, два jar-артефакта.

Точки соприкосновения с библиотекой в коде: `TelegramBot` (наследует `TelegramLongPollingBot`), `MessageSender` (держит `TelegramLongPollingBot` через `ObjectProvider` из-за циклической зависимости), `BotLifecycle` (`SmartLifecycle` с тремя попытками регистрации и остановкой с таймаутом 5 с), `BotInfrastructureConfig` (прокси в `DefaultBotOptions` и бин `TelegramBotsApi`), плюс DTO (`Update`, `Message`, `Chat`, `User`) в диспетчерах, `AiService` и `core`.

Прокси в проде не используется: `BOT_PROXY_*` пусты, журнал на каждом старте пишет «прямое подключение», а Telegram доступен через маршруты OpenVPN-клиента `tg-relay` на сервере.

## Goals / Non-Goals

**Goals:**

- Библиотека 10.3.0 без изменения наблюдаемого поведения бота: те же три попытки регистрации, та же остановка в бюджете `TimeoutStopSec`, та же асинхронная обработка обновлений.
- В приложении не остаётся ни кода, ни переменных прокси.
- Тесты остаются быстрыми и не требуют сети.

**Non-Goals:**

- Реакции на сообщения (постановка и чтение) — отдельное изменение.
- Переход на `telegrambots-springboot-longpolling-starter`: авто-конфигурация забрала бы управление регистрацией у `BotLifecycle`.
- Любые правки бизнес-логики ответов, админки и схемы базы.

## Decisions

**1. Целевая версия — 10.3.0, а не 6.9.7.1 и не 8.2.0.**
6.9.7.1 позволяет поставить реакцию без правок Java, но закрывает линию: в ней нет `allowed_updates`, поэтому чужие реакции бот не увидит, и нет возможностей Bot API 8–10. 8.2.0 — январь 2025, то есть переезд в уже устаревшую версию. 10.3.0 (Bot API 10.3, август 2026) требует Java 17, что совпадает с проектом.

**2. Ручная сборка вместо Spring-стартера.**
Стартер сам регистрирует consumer-бины и не даёт сохранить текущую семантику `BotLifecycle`: три попытки с логом, `getPhase()` для порядка остановки, ожидание `session.stop()` с таймаутом 5 с. Оставляем `SmartLifecycle` и два бина в `BotInfrastructureConfig`: `TelegramBotsLongPollingApplication` и `TelegramClient`.

**3. Клиент без прокси и без общего `OkHttpClient`.**
Так как прокси больше нет, хватает `new OkHttpTelegramClient(token)` — библиотека создаёт клиент сама. Отдельный бин `OkHttpClient` понадобится только если позже появятся таймауты или прокси; вводить его сейчас незачем.

**4. `MessageSender` получает `TelegramClient` напрямую.**
Цикл «бот → MessageSender → бот» существовал только потому, что отправителем был сам бот. Теперь клиент — отдельный бин, цикл исчезает, `ObjectProvider` и метод `getBot()` удаляются. `CallbackDispatcher` продолжает звать `messageSender.getClient().execute(answer)`.

**5. Прокси удаляется полностью, а не отключается флагом.**
Уходят запись `Proxy` с валидацией порта, бин `DefaultBotOptions` и установка системных свойств `http(s).proxyHost` / `socksProxyHost`. В проде эти свойства никогда не выставлялись, поэтому запросы к AI-провайдерам не меняются; локально при включённом TUN они тоже не нужны.

**6. Регистрация и остановка.**
`TelegramBotsLongPollingApplication.registerBot(token, consumer)` сам вызывает `BotSession.start()` (проверено байткодом 10.3.0), поэтому `BotLifecycle.start()` сохраняет цикл из трёх попыток. Если попытка бросила исключение после создания сессии, её нужно закрыть, иначе можно получить два параллельных опроса. `stop()` остаётся прежним: `session.stop()` в отдельном потоке с ожиданием 5 с.

**7. Импорты DTO.**
`objects.Message` → `objects.message.Message`, `objects.Chat` → `objects.chat.Chat`; `objects.User` и `objects.Update` остаются на месте. `CallbackQuery.getMessage()` теперь `MaybeInaccessibleMessage`, но интерфейс объявляет `getChat()`, `getChatId()` и `getMessageId()`, поэтому `CallbackDispatcher` меняется только импортом `CallbackQuery`-пути (он не изменился) — правок логики нет.

## Risks / Trade-offs

- **OkHttp вместо Apache HttpClient** → другие таймауты и поведение при обрывах. Первые сутки после деплоя смотреть журнал на `TelegramApiException` и повторы; при проблемах задать таймауты через свой `OkHttpClient`.
- **Три попытки регистрации с новой сессией** → риск двух параллельных опросов. Закрывать созданную сессию при неудаче и проверять `isRunning()`.
- **Единственная настоящая проверка — после деплоя**: деплой перезапускает живого бота. Откат — revert коммита и повторный деплой, прежняя версия библиотеки возвращается вместе с кодом.
- **Локальный запуск без TUN** перестаёт работать: прокси больше нет. Это осознанное следствие, README описывает режим TUN.
- **Версия Jackson** приходит из Spring Boot 3.5 и может отличаться от той, с которой собрана 10.3.0 → первая проверка — `mvn test`, затем поведение сериализации в журнале.

## Migration Plan

1. Ветка `feat/telegrambots-10`, правки pom и кода, `mvn test`.
2. Слияние в `main` — `Deploy bot` собирает и перезапускает службу; проверить журнал: три попытки не нужны, должна быть строка об успешном запуске и отсутствие прежней строки про прокси.
3. Смок в реальном чате: команда, обычный ответ, кнопка с callback.
4. После успешного деплоя удалить секреты `BOT_PROXY_*` в GitHub Actions и упоминания в локальных переменных Windows.
5. Откат: revert слияния и повторный пуш в `main`.

## Open Questions

Нет: что бот делает с реакциями, решается отдельным изменением и на этот дизайн не влияет.
