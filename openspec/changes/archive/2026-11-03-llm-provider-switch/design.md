# Design

## Context

Мотивация — в `proposal.md`, контракт — в `specs/llm-provider/spec.md`. Здесь только то, что определяет форму кода.

Сейчас (проверено по коду):

- `DeepSeekClient` — единственный клиент LLM: адрес берётся из константы `Settings.DEEP_SEEK_BASE_URL`, ключ — из `BotProperties.Ai.key()` (`BOT_AI_KEY`, `@NotBlank`), модель — из `bot_settings.aiModel` на каждый запрос, лимит токенов ограничен константой `MAX_ALLOWED_TOKENS = 8192`.
- `HttpClient` создаётся полем в конструкторе клиента, поэтому в тесте его не подменить.
- Список моделей — `Settings.AVAILABLE_AI_MODELS`, по нему же проверяет `AdminSettingsValidator.modelFromList`.
- Вкладка «Модель» рендерится из статического `TABS` в `AdminSettingsController`; шаблон `admin/settings.html` знает только плоский `List<String> options`.
- `BotProperties` — `record (token, db, ai, proxy, admin)`; тесты админки задают `bot.ai.key=sk-test`.
- Настройка применяется без рестарта, `StartupNotifier` печатает `Модель: <aiModel>`.
- Ключ в проде приходит из GitHub-секрета в `/etc/telegram-bot/bot.env`; файл перезаписывается на каждом деплое целиком.

## Goals / Non-Goals

**Goals:**

- Провайдер выбирается по активной модели, без хранения выбранного провайдера в состоянии.
- Каталог — единственное место, где перечислены провайдеры, модели, адреса и потолки токенов.
- Отсутствие ключа нигде не валит запуск и не молчит: видно в логе, в админке и в уведомлении о запуске.

**Non-Goals:**

- Автоматический переход на другого провайдера при сбое.
- OpenRouter и локальный сервер без ключа.
- Родной протокол Anthropic.
- Миграция БД: `aiModel` остаётся идентификатором модели без префикса.

## Decisions

### Каталог — константы в коде, а не таблица в БД

`LlmCatalog` со статическими списками:

```
Provider(String id, String title, String baseUrl, String envName, Duration timeout)
Model(String id, String providerId, String title, boolean jsonMode, int maxOutputTokens)
```

Альтернатива — таблица `llm_models`: отклонена. Ключ всё равно приходит из окружения, то есть новый провайдер без деплоя недоступен, а таблица добавляет миграцию, аудит и возможность сломать бота строкой. Комментарий в `Settings` уже фиксировал этот принцип: «список меняется вместе с кодом, а не с данными».

Уникальность идентификатора модели проверяется тестом каталога — по нему ищется модель из настроек.

### Ключи — `Map<String, String>` под `bot.ai.key`

`BotProperties.Ai(Map<String, String> key)` даёт ровно имена `BOT_AI_KEY_DEEPSEEK`, `BOT_AI_KEY_GROK`, … через релаксированный биндинг `bot.ai.key.grok`, и не требует правки `BotProperties` при добавлении провайдера. Идентификаторы берутся только из каталога, поэтому «неизвестного провайдера» в карте не бывает.

Отклонено: пять явных полей в `BotProperties.AiKeys` — пришлось бы править record на каждого нового провайдера; вложенный record `bot.ai.key` с полями по числу провайдеров — то же самое плюс шум.

`@NotBlank` у ключа снимается: отсутствие ключа — нормальное состояние (`specs/runtime-configuration`).

### Клиент один, выбор по модели

`DeepSeekClient` переименовывается в `LlmClient`. На каждый вызов:

1. модель из `settings.getModel()`, поиск в каталоге; не найдена → `ERROR` в лог и `DEFAULT_AI_MODEL`;
2. провайдер модели; ключ из карты по `provider.id()`; пусто → `ERROR` с `provider.envName()` и возврат `null` без HTTP-запроса;
3. адрес и таймаут — из провайдера, `max_tokens` — `min(настройка, model.maxOutputTokens)` с записью в лог при урезании;
4. `response_format` — только если `model.jsonMode`; существующий повтор без него при `400` сохраняется.

Второй конструктор принимает `HttpClient`, чтобы тест подменил транспорт. Альтернатива — тестировать только сборку `HttpRequest` через вынесенный метод: отклонена, она всё равно требует шва, но не проверяет фактические заголовки и адрес.

Логи называют провайдера и модель: при пяти провайдерах сообщение «DeepSeek API error» уводит в ложный след.

### Админка: группы в существующем поле, правило сохранения в валидаторе

`FieldView.options` (`List<String>`) заменяется на `List<OptionGroup>`; единственный `select` в админке — модель, поэтому шаблон всегда рендерит `<optgroup>`. Заголовок группы — отображаемое имя провайдера, у провайдера без ключа — с пометкой `— нет ключа BOT_AI_KEY_GROK`.

Валидатор получает сохранённые значения вторым аргументом и отклоняет модель, если её провайдер без ключа **и** значение отличается от сохранённого:

- переключение на безключевого провайдера — ошибка у поля, `aiModel` не меняется;
- текущее значение с исчезнувшим ключом не блокирует сохранение остальных полей вкладки.

Проверку делает валидатор, а не шаблон: `disabled` у опций закрыл бы только UI, а прямой POST её обходит.

### Уведомление о запуске

`StartupNotifier` печатает `Модель: <id> (<поставщик>)` и при отсутствии ключа добавляет `, ключа нет`. Название провайдера берётся из каталога, чтобы текст не расходился с админкой.

### Каталог: стартовое наполнение

Проверено по документации и публичному реестру моделей (litellm `model_prices_and_context_window.json`, который ссылается на `api.x.ai/v1/language-models`): DeepSeek — `deepseek-flash`, `deepseek-v4-pro` (`deepseek-chat` в документации отсутствует); Grok — `grok-4.7`, `grok-4.5`, `grok-4.3`; OpenAI — `gpt-5.6`, `gpt-5.2`, `gpt-4o`; Mistral — `mistral-large-4-0`, `mistral-small-4-0-26-03`, `ministral-3-14b-25-12`; Gemini — `gemini-4-argon` (выход до 65K), `gemini-3.8-flash`, `gemini-3.1-pro-preview`. Документация xAI и OpenAI с рабочей машины отдаёт `403`, поэтому эти два списка сверены по реестру, а не по консоли провайдера.

## Risks / Trade-offs

- **В проде `aiModel` может быть `deepseek-chat`** → модель исчезает из каталога, запросы уходят с моделью по умолчанию, и поведение меняется молча. Mitigation: до правки каталога посмотреть значение в `bot_settings`; модель по умолчанию — тоже `deepseek-flash`, так что подмена хотя бы безопасна, но о ней сообщает лог.
- **Переименование env-переменной**: `bot.env` пишется до `scp` jar, поэтому упавший деплой оставит новый env при старом jar. Mitigation: в релизном коммите оставить обе строки (`BOT_AI_KEY` и `BOT_AI_KEY_DEEPSEEK`), удалить старую отдельным коммитом после зелёного деплоя.
- **Провизорные идентификаторы Grok/OpenAI** → ошибка `model not found` от провайдера на первом же запросе. Mitigation: сверить в консоли и покрыть тестом «каждая модель каталога имеет непустые id, провайдера, адрес и потолок».
- **Температура**: у части моделей допустимый диапазон уже, чем 0..2, и запрос с 1.4 может получить `400`. Mitigation: проверить при реализации; если диапазон уже — ограничивать в каталоге и дописать сценарий в спецификацию.
- **Gemini через режим совместимости** может не знать `response_format`. Mitigation: флаг `jsonMode` в каталоге и существующий повтор без `response_format` при `400`.
- **Пять ключей в GitHub-секретах** — ручная работа владельца; недоступный секрет даёт пустую переменную, что по контракту означает «ключа нет», а не сбой.

## Migration Plan

1. Владелец добавляет секреты репозитория: `DEEPSEEK_API_KEY` (уже есть), `XAI_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `MISTRAL_API_KEY`.
2. Проверить `SELECT value FROM bot_settings WHERE setting_key = 'aiModel'`; если там `deepseek-chat` — переключить на `deepseek-flash` до деплоя.
3. Коммит: новый код + `deploy.yml` с `BOT_AI_KEY_<ID>` и временно сохранённой строкой `BOT_AI_KEY`.
4. Локальная проверка: `BOT_AI_KEY_DEEPSEEK` в окружении, сборка, запуск jar, ответ в чате.
5. Пуш в `main`, дождаться зелёного деплоя, проверить в `journalctl` строку модели и уведомление о запуске.
6. Отдельным коммитом убрать `BOT_AI_KEY` из `deploy.yml`.

Откат: реверт коммита; база не меняется, миграций нет. Если после переключения модель не отвечает, вернуть прежнюю модель в админке — список прошлой версии этого не запрещает.

## Open Questions

- Точные идентификаторы моделей Grok и OpenAI — сверяются в консоли провайдера при реализации.
- Урезать ли температуру по каталогу — зависит от ответа провайдера на значения выше его диапазона.
