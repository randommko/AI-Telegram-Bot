# Design

## Context

На VPS работают три службы: AI-бот (`telegram-bot`), его админка (`telegram-bot-admin`) и Fun-бот (`fun-telegram-bot`). Прямой доступ к Telegram с этого сервера недоступен, поэтому оба бота ходят в API через клиентский OpenVPN-туннель `openvpn@tg-relay` (устройство `tun-tg`, провайдер vpnd.io, UDP 60443). Маршруты Telegram (`91.108.4.0/22`, `91.108.8.0/22`, `91.108.12.0/22`, `91.108.16.0/22`, `91.108.20.0/22`, `91.108.56.0/22`, `149.154.160.0/20`, `91.105.192.0/23`, `185.76.151.0/24`, `95.161.76.100/32`) заворачиваются в туннель, остальной трафик идёт напрямую. Запущенный на той же машине `openvpn-server@server` (10.8.0.0/24, порт 1194) обслуживает внешних клиентов и к ботам отношения не имеет.

## Goals / Non-Goals

**Goals:**

- Ограничить паузу между повторами `getUpdates` тремя минутами, чтобы после восстановления сети бот возвращался к работе без ручного вмешательства.
- Сохранить штатное поведение библиотеки: рост паузы от 500 мс до 60 с, случайный разброс, сброс паузы после успешного запроса.

**Non-Goals:**

- Управлять инфраструктурой туннеля из кода приложения: адреса в `/etc/hosts` и nameserver — конфигурация сервера, а не репозитория.
- Менять схему регистрации бота, три попытки старта и остановку по SIGTERM.
- Трогать Fun-бот с его `TelegramBotsApi(DefaultBotSession.class)`.

## Decisions

### Свой `BackOff` вместо ожидания библиотечного умолчания

`TelegramBotsLongPollingApplication` принимает `Supplier<BackOff>` только в четырёхаргументном конструкторе; сеттера нет. Поэтому бин создаётся так:

```java
new TelegramBotsLongPollingApplication(
        ObjectMapper::new,
        new TelegramOkHttpClientFactory.DefaultOkHttpClientCreator(),
        Executors::newSingleThreadScheduledExecutor,
        () -> new ExponentialBackOff.Builder()
                .setMaxElapsedTimeMillis(MAX_RETRY_PAUSE_MILLIS)
                .build());
```

Первые три аргумента дословно повторяют умолчания конструктора `TelegramBotsLongPollingApplication()`; расхождение с библиотекой зафиксировано комментарием в коде.

### Потолок 180000 мс

`ExponentialBackOff.nextBackOffMillis()` возвращает `maxElapsedTimeMillis`, когда с момента сброса прошло больше этого значения. При 180000 мс это ровно три минуты: до третьей минуты пауза растёт 0.5 с → 60 с, дальше каждый повтор — 3 минуты. Успешный `getUpdates` вызывает `backOff.reset()`, поэтому после восстановления связи пауза снова начинается с 500 мс.

### Рассмотренные альтернативы

- **Внешний watchdog с рестартом службы.** Лечит симптом, требует таймера и прав на сервере, даёт лишний простой на старте приложения. Отклонено.
- **Свой цикл опроса вместо `BotSession`.** Дублирует код библиотеки (deleteWebhook, разбор ответа, фильтр по `update_id`) и ломает жизненный цикл из `application-bootstrap`. Отклонено.
- **Уменьшить ещё и `maxIntervalMillis`.** Не влияет на 15-минутный потолок: он определяется `maxElapsedTimeMillis`. Не требуется.

## Risks / Trade-offs

- **Три аргумента конструктора повторяют умолчания библиотеки.** При обновлении `telegrambots` умолчания могут измениться, и бот разойдётся с ними. Смягчение: комментарий в коде и эта запись; при переезде на новую версию сверить конструктор.
- **Больше запросов при длительной недоступности.** Вместо 4 попыток в час будет 20 — для одного бота это несущественно и не создаёт нагрузки на Telegram.
- **Закреплённые адреса в `/etc/hosts` устареют, если vpnd.io сменит IP.** Это инфраструктурный риск, не относящийся к коду: туннель снова упадёт, а боты будут недоступны. Смягчение: при смене адресов пересчитать их через DNS-over-TCP и поправить `/etc/hosts`.

## Migration Plan

1. Правка `BotInfrastructureConfig` (коммит `82b5ae4`).
2. Вливание в `main` — пуш запускает `Deploy bot` (сборка `-pl bot -am clean package -DskipTests`, загрузка jar и env-файла, `systemctl restart telegram-bot`).
3. Проверка после деплоя: служба `active`, в журнале нет исключений, бот отвечает в чате.

Откат — revert коммита и повторный деплой; данные и схема не затрагиваются.
