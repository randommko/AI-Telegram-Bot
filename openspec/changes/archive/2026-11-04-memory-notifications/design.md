# Design

## Context

См. `proposal.md` — почему. Техническая обстановка:

- `AiMemoryExtractor.analyzeChat` уже держит в руках всё нужное для отчёта: `existing` (активные записи с текстом, категорией, важностью, id), `extraction` (черновики add/update), `applied` (после фильтра защищённых удалений) и `rejected` (отброшенные id). Тексты удаляемых записей есть в `existing` — отдельный запрос не нужен.
- `analyzeChat` вызывается из двух мест: планировщика `analyzeDueChats` (фон) и кнопки в `AdminMemoryController`; ручные правки формы идут мимо него.
- Личка владельца — настройка `ownerChatId` в `bot_settings`; `StartupNotifier` читает её так: пусто/не число → уведомления выключены, `WARN` в лог.
- `MessageSender.sendLongMessage` режет текст и не бросает исключение при сбое одной части.
- Страница настроек собирает форму из `FieldView` с видами `text`, `textarea`, `select`, `radio`, `range`, `hidden`; вид «флажок» отсутствует, хотя в карточке персоны флажки (`initiativeEnabled`) уже используются.
- Миграции — ручные SQL; INSERT-настройки бот переживает без схемных изменений.

## Goals / Non-Goals

**Goals:**

- Показать в одном сообщении, что именно изменилось в памяти, не открывая админку.
- Отправлять отчёт после успешной записи, чтобы сбой доставки никогда не влиял на память.
- Дать владельцу выключатель, не трогая сам анализ.

**Non-Goals:**

- Уведомления о ручных правках и о действиях модераторов — это журнал `admin_changes`, отдельная тема.
- Дамп разобранной переписки и цитаты сообщений в личке.
- Накопительный дайджест по нескольким персонам одним сообщением: отчёт всегда про один прогон одного чата.
- Настройка получателя отдельно для памяти: используется существующий `ownerChatId`.

## Decisions

### Отдельный отправитель `MemoryUpdateNotifier`, а не код внутри экстрактора

Форматирование и отправка выносятся в компонент, который принимает имя персоны, чат, `existing`, `applied`, `rejected` и счётчики. Экстрактор остаётся про анализ.

Альтернативы: (а) собрать текст прямо в `analyzeChat` — короче на один класс, но формат не протестировать без прогона модели и моков LLM; (б) сервис с очередью и повторами — лишняя инфраструктура для одного сообщения.

### Тексты удалённых записей берутся из уже прочитанного `existing`

`existing` — это все активные воспоминания персоны до транзакции, значит по id из `extraction.delete()` там есть текст, категория и важность. После `apply` эти записи уже помечены удалёнными и из выборок исчезают.

Альтернатива — `findDetails(id)` на каждое удаление: лишние запросы и гонка, если запись успели удалить между чтением и отправкой.

### Отправка после `apply`, вне транзакции

Сначала память и отметка коммитятся, затем отправляется сообщение. `MemoryUpdateNotifier` сам ловит исключения и пишет `WARN`; экстрактор дополнительно оборачивает вызов, чтобы даже неожиданная ошибка форматирования не сорвала анализ.

Альтернативы: отправка до `apply` — сообщение о том, что не сохранилось; отправка внутри транзакции — сбой Telegram откатил бы память.

### Имя персоны — `personaRepository.findForChat(chatId)`

Один дополнительный запрос на прогон (раз в ~50 сообщений). Альтернатива — расширить `findAssignedChats` join'ом с `personas`, но `ChatPersona` используется и в других местах, а менять общую запись ради заголовка сообщения невыгодно.

### Название чата читается безопасно

`ChatsService.getChatTitle` падает, если чата нет в `tg_chats`. Отчёт берёт название через тот же сервис, но при пустом результате или исключении подставляет `чат <id>`; id в заголовке есть всегда.

### Нулевые изменения не уведомляются

Если `applied.add/update/delete` пусты, сообщения нет. Порог `aiMemoryAnalyzeEvery` и так даёт прогон раз в 50 сообщений, а пустые отчёты только шумят.

### Флажок в настройках — новый вид поля `checkbox`

`FieldView` получает вид `checkbox`, шаблон — блок с `<input type="checkbox">` и скрытым `false` перед ним. Без скрытого поля снятый флажок не попадёт в запрос, а `submitted()` сохранит пустую строку; скрытое поле перед галочкой даёт `false`, когда она снята, и `true`, когда стоит.

Альтернативы: `select` с «Да/Нет» — работает без правки шаблона, но для булева значения читается хуже; `radio` — ещё громоздче.

### Ключ `aiMemoryNotifyOwner`, по умолчанию включён

Читается как «включено», если строка отсутствует или пуста; выключает только явное `false`. Значение заводит INSERT-миграция с описанием — оно же становится подсказкой (i) у поля. `ON CONFLICT DO NOTHING` делает миграцию идемпотентной.

### Ручная кнопка не требует отдельной ветки

Она вызывает тот же `analyzeChat`, поэтому отчёт уходит автоматически. Ручные правки формы не проходят через экстрактор и остаются без уведомлений — это и есть выбранная граница.

## Risks / Trade-offs

- **Шум в активном чате** → порог анализа, молчание при нулевых изменениях, флажок в админке.
- **Личные факты уходят в Telegram** → получатель — приватная личка владельца (`ownerChatId`), то есть тот же человек, который видит память в админке; модератор настройку не видит и не меняет.
- **Слишком длинный отчёт** → `sendLongMessage` режет по границе и отправляет частями; отчёт всё равно один прогон.
- **Падение `getChatTitle` на неизвестном чате** → безопасное чтение с запасным `чат <id>`.
- **Сбой отправки скрыт от владельца** → в лог пишется `WARN` с чатом и персоной; память уже сохранена, следующий прогон работает как обычно.
- **Флажок не сохраняет «выключено»** → проверяется тестом `AdminSettingsTest` на снятый флажок и повторное открытие вкладки.

## Migration Plan

1. INSERT-миграция `bot_settings` (`aiMemoryNotifyOwner = true`, описание) — применяется до пуша вместе с кодом; таблицу не меняет.
2. Пуш в `main` пересобирает и перезапускает бота; первый фоновый анализ после порога пришлёт первое сообщение, если были изменения.
3. Откат — revert коммита; лишняя строка `bot_settings` безвредна и останется, пока её не удалят.
