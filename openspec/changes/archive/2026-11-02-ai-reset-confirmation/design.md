# Design

## Context

Мотивация — в `proposal.md`, требования — в дельте `specs/ai-chat-memory/spec.md`. Что важно для реализации:

- Команда `/clear` уже существует: `CommandDispatcher` (`AI_CLEAR_HISTORY`, обработчик `handleAiChatHistory`) сразу вызывает `AiService.clearChatHistory` и показывает два сообщения с `Thread.sleep(1000)` между ними.
- Inline-клавиатура в проекте одна — зодиаки в `KeyboardBuilder`; подтверждений нет ни одного.
- `CallbackDispatcher.dispatch` централизованно вызывает `answerCallbackQuery` после каждого хендлера, но без текста — хендлер не может передать всплывающее уведомление.
- `MessageSender.editMessage(chatId, msgId, text)` существует, но нигде не используется и не убирает клавиатуру.
- Апдейты обрабатываются в пуле потоков (`TelegramBot.onUpdateReceived`), поэтому `Thread.sleep` в хендлере поток не блокирует — он просто задерживает ответ и держит поток впустую.
- Принцип из `make-app-stateless`: состояние не живёт в памяти процесса, иначе рестарт его теряет.

## Goals / Non-Goals

**Goals:**

- Сброс выполняется только после явного согласия автора команды.
- Ни отказ, ни чужое нажатие не меняют историю и счётчик сбросов.
- После ответа на вопрос клавиатура исчезает, повторно нажать кнопку нельзя.
- Никакого состояния в памяти процесса между вопросом и нажатием.

**Non-Goals:**

- Изменение самой очистки (`AiChatRepository.clearMessages`, `incrementResets`), лимита истории и счётчика сбросов.
- Права на саму команду `/clear`: кто может её вызвать, не обсуждается.
- Переименование команды и общий механизм подтверждений для других команд.

## Decisions

### 1. Автор команды передаётся в `callback_data`, а не хранится в памяти

Telegram возвращает в callback только `callback_data` и само сообщение, поэтому id автора нужно доставить вместе с кнопкой. Формат: `aiClear:yes:<userId>:<N>` и `aiClear:no:<userId>:<N>`, где N — число сообщений в истории на момент команды: без него итоговое «забыто N» пришлось бы пересчитывать уже после удаления. 30–40 байт при 19-значном id — лимит Telegram в 64 байта соблюдён.

Альтернативы:
- `Map<messageId, authorId>` в памяти — ровно то состояние, от которого отказались в `make-app-stateless`: рестарт между вопросом и нажатием теряет автора.
- Таблица в БД — новая миграция ради одного числа, которое помещается в callback.

Разбор строки — маленький парсер рядом с клавиатурой (аналог `Zodiac.fromCallback`), возвращающий действие и id автора; нераспознанный `callback_data` уходит в существующую ветку «Неизвестная кнопка».

### 2. Клавиатура строится в `KeyboardBuilder`

Туда же, где живут зодиаки: один класс на все inline-клавиатуры, по образцу `sendHoroscopeKeyboard` — метод отправляет сообщение-вопрос с разметкой и сам считает текст.

### 3. `CallbackHandler` возвращает текст уведомления

Сейчас `dispatch` после хендлера вызывает `answerCallbackQuery(callback)` без текста. Чтобы показать «эту кнопку нажимал другой пользователь», хендлер должен вернуть строку: интерфейс становится `String handle(...)`, `dispatch` передаёт результат в `answerCallbackQuery(callback, toast)`, существующие хендлеры возвращают `null`.

Альтернатива — хендлер сам вызывает `AnswerCallbackQuery`: тогда `dispatch` ответит вторым запросом, Telegram вернёт «query is too old» и в лог уедет ошибка на каждый клик.

### 4. После действия сообщение редактируется, клавиатура убирается

Используется `CallbackQuery.getMessage()` (id и чат сообщения-вопроса), поэтому id отправленного сообщения запоминать не нужно. `MessageSender.editMessage` дополняется очисткой inline-клавиатуры (`InlineKeyboardMarkup` с пустым списком), иначе после «Да» или «Отмена» кнопки остаются живыми: повторное «Да» снова обнулит память и увеличит счётчик.

Если сообщение уже удалено или слишком старое, `TelegramApiException` логируется, хендлер не падает — сброс к этому моменту уже выполнен.

### 5. Порядок проверок в хендлере

`callback_data` → сверка `callback.getFrom().getId()` с id из данных → действие. При несовпадении сообщение не редактируется и история не трогается: иначе чужой человек мог бы «отменить» чужой сброс.

Сам хендлер живёт в `CallbackDispatcher`, поэтому этот класс получает зависимость `AiService` (сейчас у него только отправитель, гороскоп и игра размеров) — подтверждение вызывает `clearChatHistory` там же, где обрабатывается нажатие.

### 6. Число забытых сообщений считается в момент команды

`getChatHistorySize` вызывается при отправке вопроса, это же число показывается в вопросе, уезжает в `callback_data` кнопок и попадает в итоговое «забыто N». Сообщения, пришедшие между вопросом и подтверждением, тоже удаляются, но N их не учитывает — так требует спека («в момент команды»), а гонка на секунды не стоит второго запроса к БД.

### 7. `Thread.sleep(1000)` удаляется

Обе паузы нужны были только чтобы растянуть три отдельных сообщения. При подтверждении остаётся одно сообщение, которое редактируется, — паузы не нужны.

## Risks / Trade-offs

- **`callback_data` ограничен 64 байтами** → формат держим коротким и проверяем тестом на максимальный 19-значный id.
- **Кнопки после действия остаются, если Telegram отклонит правку** (сообщение старше 48 часов или удалено) → история к этому моменту уже изменена; остаётся лог ошибки. Вероятность низкая: подтверждение нажимают сразу.
- **Правка `MessageSender.editMessage` меняет общий метод** → других вызовов нет, поведение задокументировано в задаче; если появится второй сценарий без очистки клавиатуры, понадобится перегрузка.
- **Смена интерфейса `CallbackHandler` затрагивает существующие хендлеры** → их всего два (`avg_cock_size_button_pressed` и зодиаки идут другим путём), правка механическая, компилятор покажет все места.
- **N в ответе может быть меньше фактически удалённого** → сознательный компромисс, см. решение 6.

## Migration Plan

Изменений схемы БД и конфигурации нет. Выкат — обычный: коммит в `main`, деплой собирает jar и перезапускает сервис; после деплоя подтверждение проверяется вручную в чате (`/clear` → «Отмена», затем `/clear` → «Да»), потому что успешный сброс пишет только `logger.info`.
