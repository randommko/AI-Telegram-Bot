# Design

## Context

Текущее состояние (см. proposal.md — Why): `Main` читает gitignored `config.json`, содержит SOCKS5-прокси код; `TelegramBot` принимает `DefaultBotOptions`; `deploy.yml` передаёт секреты аргументами, которые `Main` игнорирует; миграций БД в репо нет. Схема БД уже существует на продакшн-сервере (`45.141.103.51`), но не воспроизводима из репозитория.

## Goals / Non-Goals

**Goals:**
- Запуск конфигурируется только аргументами CLI, без прокси и без `config.json`.
- Схема БД воспроизводима через SQL-миграции в репо.
- `deploy.yml` и `Main` используют один и тот же порядок аргументов.

**Non-Goals:**
- Не меняем функциональность команд бота, игр и ИИ-чата.
- Не внедряем Flyway/Liquibase.
- Не меняем структуру таблиц, уже существующих на продакшене (только фиксируем их в миграциях).
- Не добавляем автозапуск миграций из приложения.

## Decisions

### D1: Конфигурация — аргументы CLI (а не config.json или env)

`Main.main(String[] args)` принимает ровно 5 аргументов: `token dbUrl dbUser dbPassword aiKey`. При отсутствии/пустом значении — лог ошибки и `System.exit(1)`.

**Альтернативы:** env-переменные (безопаснее — не видны в `ps`, но требуют правки и `Main`, и `deploy.yml`); оставить `config.json` (генерировать на VPS из секретов — больше движущихся частей). Выбран CLI-путь: `deploy.yml` уже передаёт ровно эти секреты в этом порядке, значит правки CI/CD минимальны, а секретов нет в репозитории.

### D2: Прокси удаляется полностью

Из `Main` убираются парсинг `proxy`, `System.setProperty`, `Authenticator`, создание `DefaultBotOptions`. Конструктор `TelegramBot` меняется на `(String botToken, String aiToken)` с вызовом `super()` (дефолтные опции). Удаляются `ListJar.java` и `ListJar.class` (отладочный хелпер по `ProxyType`).

### D3: Миграции — ручные SQL-скрипты без новых зависимостей

Директория `migrations/` с нумерованными `.sql` (например `001_init_schema.sql`, `002_seed_bot_settings.sql`). Накатываются вручную через `psql`. Схему снимаю с удалённой БД (`pg_dump --schema-only` или интроспекция), чтобы DDL был точным, а не реконструированным из кода.

**Альтернатива:** Flyway (автоприменение при старте) — отклонено: добавляет зависимость, а продакшн-схема уже существует и её проще зафиксировать как baseline.

### D4: Идемпотентность миграций

Все `CREATE TABLE IF NOT EXISTS`, seed-данные через `INSERT ... ON CONFLICT DO NOTHING`. Это безопасно повторно накатывать на уже заполненную прод-БД без потери данных.

### D5: seed для `bot_settings`

Без ключей `aiAnswerTemperature`, `maxTokensQuestion`, `aiPromtContext`, `aiPromtMyChatContext` поля `AiService`/`DeepSeekClient` инициализируются `Float.valueOf(null)`/`Integer.valueOf(null)` → NPE на старте. Значения этих ключей снимаю с существующей прод-БД (или задаю разумные дефолты), чтобы локальный запуск не падал.

### D6: CI/CD

`deploy.yml` уже вызывает `java -jar ... <TOKEN> <DB_ADDR> <DB_USER> <DB_PASS> <DEEPSEEK_API_KEY>` из GitHub Secrets. Выравниваю только под новый порядок аргументов `Main` (при необходимости) и оставляю inject секретов как есть.

## Risks / Trade-offs

- **Удалённая БД может блокировать подключение с локальной машины** (`pg_hba.conf`/firewall порта 5432) → Снять схему можно с VPS (`ssh ... pg_dump --schema-only`), а миграции накатывать на VPS.
- **Пароль БД в команде запуска виден в `ps` и истории shell** → Для CI/CD пароль хранится в GitHub Secrets; для локального запуска это приемлемо, пароль рекомендуется ротировать после попадания в чат.
- **Удаление прокси может изменить сетевое поведение**, если на VPS Telegram был доступен только через прокси → Проверить прямой запуск; при необходимости вернуть прокси отдельным изменением (в текущем коде прокси был SOCKS5 и, судя по коммитам, больше не используется).
- **Seed-значения `bot_settings` неизвестны до интроспекции** → Снять их с прод-БД до написания миграции; при недоступности — задать дефолты и пометить для ручной сверки.

## Migration Plan

1. Снять текущую схему и seed `bot_settings` с удалённой БД.
2. Оформить `migrations/*.sql` (идемпотентные).
3. Применить миграции локально/на VPS и проверить запуск.
4. Задеплоить через обновлённый `deploy.yml`.

Откат: миграции только аддитивные и идемпотентные, разрушающих операций нет — откат сводится к откату кода, данные не теряются.
