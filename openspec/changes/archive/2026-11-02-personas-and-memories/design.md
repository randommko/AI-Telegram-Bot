# Design

## Context

- Персона сейчас — строка промпта: `AiService.getSystemPrompt` выбирает `aiPromtMyChatContext` для `MY_CHAT_ID`, иначе `aiPromtContext`, иначе `DEFAULT_SYSTEM_PROMPT`. Читается на каждый запрос.
- Обращение распознаёт `AiAddressParser` по константе `юра|юрец|юрчик|юрий|юр`, только с начала строки. `CommandDispatcher.answerNameAddress` дополнительно гейтит `MY_CHAT_ID`.
- `AiService.askAi(chatId, userQuestion)` аргумент `userQuestion` использует только для проверки на пустоту: в запрос уходят системный промпт, счётчик сбросов и сохранённые `ai_messages`. То есть «вопрос» — это выключатель, а не полезная нагрузка.
- История — плоский лог `ai_messages` (`migrations/003_ai_history.sql`), окно на чат из `aiHistorySize` = 100, обрезка при вставке. Автор сообщения уже внутри `content` префиксом `Сообщение от: @nick: текст`.
- Репозитории — JDBC (`DataSource` + `PreparedStatement`), без ORM и без `@Transactional`. Миграции — ручные идемпотентные SQL-скрипты, накатываются `psql` от владельца схемы.
- `@EnableScheduling` и `@Scheduled` в проекте не используются. `HttpClient` в `DeepSeekClient` без таймаутов, `max_tokens` берётся из `maxTokensQuestion` один раз в конструкторе, модель `deepseek-flash` зашита константой.
- `BOT_ID_PROD`/`BOT_ID_TEST` в `Settings` не используются нигде.
- Тесты — JUnit 5 + Mockito, без БД. См. `openspec/specs/persona/spec.md` и `persona-memory/spec.md` для требуемого поведения; мотивация — в `proposal.md`.

## Goals / Non-Goals

**Goals:**

- Схема, на которую смогут опереться #51 (настроение, обиды) и #57–#61 (админка), без повторных миграций под них.
- Персона и память читаются из БД на каждый запрос — правки применяются без рестарта.
- Анализ переписки не блокирует ответ пользователю и не дублирует уже разобранное после рестарта.
- Всё новое покрывается unit-тестами без введения тестовой БД.

**Non-Goals:**

- Использование `persona_state` и `persona_grudges` в ответах — это #51; таблицы создаются заранее и до тех пор остаются неиспользуемыми.
- Полнотекстовый поиск по истории как источник контекста — #51/#63; индекс создаём, но не читаем.
- Инициатива персоны, настроение в промпте, смена персоны в чате с сообщением о входе/выходе — #51/#60.
- Персона в чатах, отличных от `MY_CHAT_ID` — #62.
- Бэкфилл воспоминаний из старой переписки: анализируется только удержанное окно.

## Decisions

### D1. Миграция `004_personas_and_memories.sql` — аддитивная и идемпотентная

Девять таблиц из #53 (`personas`, `persona_aliases`, `chat_personas`, `memory_categories`, `persona_memories`, `memory_people`, `memory_analysis_state`, `persona_state`, `persona_grudges`), частичный индекс `persona_memories_core_idx ... WHERE is_core`, индекс под топ-N `(persona_id, importance DESC, event_date DESC NULLS LAST)`, GIN-индекс `to_tsvector('russian', content)` по `ai_messages.content`. В конце — тот же блок `GRANT`/`ALTER DEFAULT PRIVILEGES` для `app_user`, что в 003, с `EXCEPTION WHEN insufficient_privilege` и `NOTICE`.

*Альтернативы:* Flyway/Liquibase — отвергнуто ранее и подтверждено: проект сознательно живёт на ручных скриптах; одна миграция на все таблицы вместо девяти файлов — правки вносятся одним прогоном и не оставляют полуприменённого состояния.

### D2. Алиас уникален в пределах персоны

`UNIQUE (persona_id, alias)` вместо глобального `unique` и индекс по `lower(alias)` для поиска. Причина: разрешение идёт по персоне чата, поэтому две персоны в разных чатах вправе откликаться на одно имя; глобальная уникальность заблокировала бы это ещё до #62.

*Альтернатива:* глобально уникальный алиас — отвергнуто: ограничение не соответствует модели «одна персона на чат», а обходится переименованием в админке.

### D3. Персона «Юра» переносится из настройки, а не из кода

```sql
INSERT INTO public.personas (name, prompt)
SELECT 'Юра', value FROM public.bot_settings
WHERE setting_key = 'aiPromtMyChatContext' AND btrim(value) <> ''
ON CONFLICT (name) DO NOTHING;
```

Дальше `persona_aliases` (`юр`, `юра`, `юрец`, `юрчик`, `юрий`) и `chat_personas` для `-1001347887839` — только если персона реально создалась (`INSERT ... SELECT ... WHERE EXISTS`). Текст промпта в git не попадает, PII остаётся в БД.

*Риск и проверка:* если настройка пуста, персона не появится, и обращение по имени в синем чате молча перестанет работать. После накатки обязателен `select name, length(prompt) from personas` и `select count(*) from chat_personas`.

### D4. Источник промпта — персона, затем настройка, затем дефолт

`PersonaService.promptFor(chatId)` возвращает промпт персоны с непустым текстом; иначе прежняя цепочка `MY_CHAT_ID ? aiPromtMyChatContext : aiPromtContext`; иначе `DEFAULT_SYSTEM_PROMPT`. В лог — каким источником воспользовались (`persona:<name>` / `setting:<key>` / `default`), чтобы вопрос «почему бот отвечает не так» решался по `journalctl`.

*Альтернатива:* оставить `aiPromtMyChatContext` приоритетнее персоны — отвергнуто: тогда админка #58 редактирует промпт, который ни на что не влияет.

### D5. Алиасы читаются из БД на каждый запрос, парсер их принимает аргументом

`PersonaService.aliasesFor(chatId)` возвращает список; `AiAddressParser.question(text, aliases)` компилирует `(?<![\p{L}\p{N}])<quoted>(?![\p{L}\p{N}])`, альтернация с `Pattern.quote`, регистр не важен через `(?iu:...)`. Порядок альтернатив не важен: правая граница не даёт `юр` сработать внутри `юрчик`. Пустой список — обращений нет.

`question` возвращает `Optional<String>`: исходный текст, если после вычитания алиаса и прилегающих разделителей что-то осталось, и пустую строку, если сообщение состоит только из имени. Сам текст в модель не подставляется — он уже в истории.

*Альтернативы:* кеш алиасов с TTL — отвергнуто (нужна немедленная применимость правок); поиск по началу строки — отвергнуто требованием #54; вырезание имени из отправляемого текста — отвергнуто: текст уходит в историю до вызова AI и вырезать его пришлось бы уже из запроса.

### D6. Реплай определяется по id самого бота из токена

`BotProperties` получает `botId()` = часть токена до `:`. Условие триггера: `replyToMessage != null && reply.getFrom() != null && reply.getFrom().getId().equals(botId)`. Гейт `MY_CHAT_ID` остаётся общим для имени и реплая.

*Альтернативы:* `reply.getFrom().getIsBot()` — отвергнуто: в группе может быть другой бот; `BOT_ID_PROD`/`BOT_ID_TEST` — отвергнуто: мёртвые константы, не совпадут с локальным тестовым токеном.

### D7. Фоновый анализ — `@Scheduled(fixedDelay = 5 минут)` по привязанным чатам

`@EnableScheduling` на `Main`. Каждый тик: `chat_personas` → для каждого чата watermark (0, если строки нет) → `count(*) WHERE chat_id = ? AND id > watermark`; меньше `aiMemoryAnalyzeEvery` — пропуск. Если порог больше `aiHistorySize`, в лог `WARN`: анализ физически не сможет увидеть столько сообщений. Ошибка одного чата ловится и логируется, цикл продолжается.

*Альтернативы:* проверка на каждом входящем сообщении — отвергнуто: блокирует ответ пользователю и требует лишней записи на каждое сообщение; отдельная таблица счётчиков — отвергнуто как дублирование watermark.

### D8. Хвост читается один раз, watermark двигается до максимума прочитанного

Перед вызовом модели читается хвост `id > watermark` (по возрастанию) и запоминается `maxId`. Сообщения, пришедшие во время анализа, получат больший `id` и попадут в следующий прогон — они не теряются и не анализируются дважды.

Разрыв окна детектируется до чтения хвоста: если `min(id)` в чате больше `watermark + 1` и сообщений в таблице ровно столько, сколько разрешает `aiHistorySize`, значит часть переписки уже удалена обрезкой. Логируется `WARN` с `watermark`, `min(id)` и количеством доступных сообщений; точное число потерянных сообщений не вычисляется — `id` глобальные и удалённые строки невосстановимы.

### D9. Контракт анализа — строгий JSON, валидация до записи, одна транзакция

Модель получает: промпт анализа из `aiMemoryExtractPrompt`, существующие воспоминания персоны строкой `id | category | content | importance | core` (ядро помечено) и новые сообщения. Ожидаемый ответ:

```json
{"add":[{"category":"хобби","content":"…","importance":6,"event_date":"2025-11-01","people":["@andrew"]}],
 "update":[{"id":12,"category":"работа","content":"…","importance":8,"event_date":null,"people":[]}],
 "delete":[{"id":13}]}
```

Перед разбором снимаются обёртки ```` ```json ````/```` ``` ````; невалидный JSON или отсутствие ключей — ошибка прогона. Валидация: категория ищется в справочнике (неизвестная → «другое», `WARN`), `importance` клампится в 1..10, `event_date` парсится как ISO или становится `null`, `people` ищутся в `tg_users` по `user_name`/`first_name` (снимается `@`, регистр не важен), неизвестные пропускаются с `WARN`, `update`/`delete` с несуществующим `id` пропускаются с `WARN`.

Запись — один `Connection` с `setAutoCommit(false)`: добавления, обновления, удаления, связи `memory_people` и `last_message_id`; `commit` в конце, `rollback` при любом исключении. `source = 'auto'` для всего, что создал анализ.

*Альтернативы:* несколько запросов без транзакции — отвергнуто: при падении посередине watermark съедет или память станет половинчатой; `@Transactional` — не используется в проекте, а `AiChatRepository` уже работает с `DataSource` напрямую.

### D10. Ядро защищено на уровне записи, а не промпта

`add` всегда пишет `is_core = false`. `update` обновляет поля, не трогая `is_core`. `delete` с `is_core = true` отбрасывается и логируется как `WARN` с `id` и текстом. Модель видит ядро в списке существующих и помеченным, поэтому может актуализировать факт, но не «забыть» его.

*Альтернатива:* отдельная колонка `protected`/отдельная таблица — отвергнуто: `is_core` уже требуется #53, #56 и админкой #59.

### D11. Память — отдельное system-сообщение между промптом и историей

`MemoryPromptBuilder` собирает строку из двух блоков: «Что ты помнишь о себе и о людях в чате всегда (это незыблемо)» и «Что ты помнишь о себе и о людях в чате»; формат строки — `- [категория] текст (важно: N, дата, @nick)` с датой и людьми только при наличии. `AiService.getHistoryInChat` добавляет её вторым system-сообщением после промпта персоны и до счётчика сбросов. Нет персоны или нет воспоминаний — сообщения нет.

*Альтернативы:* склеить промпт и память в одно сообщение — отвергнуто: отдельный блок проще тестировать, логировать по символам и позже заменить на другую структуру; добавить память в историю как отдельные строки — отвергнуто, `ai_messages` про переписку, а не про системный контекст.

### D12. Анализ ходит тем же клиентом, но со своими параметрами

`DeepSeekClient` получает перегрузку с явными `temperature` и `max_tokens`: для анализа 0.2 и 2000. Модель остаётся глобальной константой (перенос в настройки — #49). Пустой `content` при `finish_reason = length` считается ошибкой прогона, watermark не двигается.

*Альтернативы:* переиспользовать `maxTokensQuestion` (500) — отвергнуто: `deepseek-flash` — reasoning-модель, размышления съедают бюджет и ответ приходит пустым (проверено на 5 токенах); завести отдельный HTTP-клиент — отвергнуто, различия только в двух полях.

### D13. Тестируемая логика выносится из JDBC

Чистыми классами без БД делаются: `AiAddressParser` (алиасы аргументом), `MemoryPromptBuilder` (сортировка, обрезка, форматирование), разбор и валидация ответа модели, решение «пора анализировать» по числу новых сообщений, защита ядра от `delete` (на уровне сервиса записи). SQL-выборки проверяются руками через `psql` на реальной базе, как и остальные репозитории проекта.

*Альтернатива:* Testcontainers/H2 — отвергнуто: новая зависимость и отдельный жизненный цикл ради нескольких запросов; H2 не совпадёт с PG по `NULLS LAST`, `to_tsvector` и identity.

### D14. Таймауты у HTTP-клиента

`HttpClient` получает `connectTimeout(10s)` и `HttpRequest.timeout(60s)`: в потоке ответа это просто ошибка, а в планировщике — иначе подвешенный тик. Ошибка анализа уже покрыта политикой «ничего не пишем, watermark не двигаем».

## Risks / Trade-offs

- **Промпт синего чата меняет источник** → после миграции правка `aiPromtMyChatContext` перестаёт влиять; в логе видно `persona:Юра`. Осознанно, закрывается админкой #58.
- **Простой бота дольше окна истории** → часть переписки не будет проанализирована; пишем `WARN` с границами, восстановить нельзя.
- **Стоимость** → один дополнительный запрос к модели на 50 сообщений чата; при текущем трафике это единицы запросов в сутки.
- **Reasoning съедает бюджет анализа** → 2000 токенов на ответ; пустой ответ трактуется как ошибка, а не как «нечего запоминать», поэтому память не портится молча.
- **Память — это PII о людях чата** → хранится в БД, в репозиторий попадают только структура и промпт анализа, сид персоны читает текст из `bot_settings`.
- **Рост системного промпта** → ядро не ограничено, обычные ≤ 30; при 5–10 ядровых записях это несколько тысяч символов, в пределах контекста.
- **Обрезка истории и анализ в одном чате** → обрезка при вставке не блокирует чтение хвоста, но может укоротить его между тиками; разрыв логируется (D8).
- **Мёртвые до #51 таблицы и индекс** → `persona_state`, `persona_grudges`, GIN-индекс по `ai_messages` не используются, стоят немного на вставке. Осознанно: схема под #51 закладывается сейчас, чтобы не делать вторую миграцию подряд.
- **`@Scheduled` на одном потоке** → анализ по чатам идёт последовательно; при нескольких чатах с персонами (#62) тик может не укладываться в 5 минут, `fixedDelay` просто отложит следующий — данные не потеряются.

## Migration Plan

1. Применить `migrations/004_personas_and_memories.sql` на рабочую БД через `psql` от владельца схемы **до** пуша: новый код без таблиц не поднимется.
2. Проверить: 9 таблиц, `select name, length(prompt) from personas`, алиасы, `chat_personas` для `-1001347887839`, ключи `aiMemoryPromptSize`/`aiMemoryAnalyzeEvery`/`aiMemoryExtractPrompt`, `select` из новых таблиц под `app_user`.
3. Первый пуш (схема + персона + обращение, #53/#54): jar → бут-чек → деплой. Смоук в синем чате: «юра, привет», «как дела, юра?», «юрист — это профессия», реплай на ответ бота, `/ai` и `/clear` работают как раньше.
4. Второй пуш (анализ + память в промпте, #55/#56): после 50 сообщений в чате проверить появление строк в `persona_memories` и по логу — количество ядровых и обычных воспоминаний в промпте.
5. Откат: revert коммитов; миграция аддитивная, старый код новые таблицы игнорирует, а промпт снова берётся из `aiPromtMyChatContext`.

## Open Questions

- Ручной прогон анализа из админки относится к #59; здесь достаточно фонового.
