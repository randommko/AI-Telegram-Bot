# Design

## Context

`AdminAccess` (`admin/src/main/java/org/example/admin/AdminAccess.java`) выводит права модератора из чатов: `canSeePersona` — есть хотя бы один чат персоны, `canEditPersona` — все её чаты выданы (`PersonaRepository.permission`). Списки берут `findAllWithCounts(visibleChats)` и `editablePersonaIds(chatIds)`. Автор персоны нигде не хранится, поэтому «создал сам» выразить нечем; выдачи персоны без чата тоже нет.

Мотивация — `proposal.md`; поведение — дельта `specs/moderator-access/spec.md`.

## Goals / Non-Goals

**Goals:**

- Разделить право на чат (просмотр персоны) и право на персону (правка, выдача владельцем).
- Хранить автора персоны и явные выдачи так, чтобы они переживали смену привязок.
- Дать владельцу один экран, где видно, кто что может, и где выдаётся доступ.

**Non-Goals:**

- Не менять права бота (`ai_user`) и поведение ответов в чате.
- Не менять выдачу чатов: `configurator.chat_moderators` остаётся как есть.
- Не давать модератору выдавать доступ другим — это право владельца.
- Не менять правило «воспоминания — по персонам, которые модератор вправе править».

## Decisions

**Автор хранится в `config.personas.created_by`.** Тип — `bigint` со ссылкой на `shared.tg_users(user_id)` и `ON DELETE SET NULL`: удаление человека не должно удалять персону. `NULL` означает «создана владельцем или ботом» — такие персоны правятся владельцем, а модератор получает их только выдачей. Альтернатива — отдельная таблица авторства — лишняя сущность ради одного поля.

**Гранты — в `configurator.moderator_personas` (tg_user_id, persona_id, granted_by, granted_at), PK по паре.** Схема `configurator` уже означает «кто в админке что может», и `admin_user` пишет туда без новых грантов. Каскад по персоне: удалили персону — выдача исчезла. Альтернатива — колонка-массив в `admin_accounts` — не даёт внешних ключей и автора выдачи.

**Видимость и правка считаются одним SQL-предикатом, а не обходом персон в Java.** Для модератора:

```
видит:   EXISTS(chat_personas в его чатах) OR created_by = он OR EXISTS(грант)
правит:  created_by = он OR EXISTS(грант)
```

Предикат живёт в `PersonaRepository` (`findAllWithCounts`, `visiblePersonaIds`), а `AdminAccess` вызывает его на одну персону. Альтернатива — грузить всех персон и фильтровать в памяти — сломается на первом же крупном списке и разойдётся с SQL-списками.

**Порядок источников в интерфейсе:** «выдан» важнее «чат» — если у модератора есть и чат, и грант, карточка правится. Источник показывается подписью, чтобы владелец видел, откуда право.

**Привязка персоны к чату требует права на персону.** `AdminChatController` уже проверяет `canEditPersona` при смене привязки; с новыми правилами модератор сможет привязать к своему чату только персону, которую создал или ему выдали. Это следствие, а не отдельная проверка.

**Обратная совместимость прав при выкатке.** Миграция выдаёт грант каждому модератору на персоны, все чаты которых уже принадлежат ему, — ровно те, что он правил по старому правилу. Иначе после выкатки он потерял бы правку и ждал бы выдачи от владельца. Вставка идемпотентна (`ON CONFLICT DO NOTHING`).

**Чтение без права не скрывается, если есть чат.** Карточка персоны своего чата остаётся доступной: модератору нужно видеть, как персона выглядит в его чате. Форма показывает пояснение вместо кнопки «Сохранить». Альтернатива — прятать такие персоны — сломала бы сценарий «посмотреть, кого привязали».

## Risks / Trade-offs

- **Модератор видит чужую персону и не может её поправить** → подсказка в карточке прямо говорит, что правку выдаёт владелец; владелец выдаёт доступ одним кликом в «Модераторах».
- **Владелец получает больше ручной работы** → обратный бэкфилл грантов сохраняет текущие права, а выдача — один select и одна кнопка на учётку.
- **`created_by` не знает прошлое**: персоны, созданные модераторами до миграции, останутся с `NULL` — их права восстановит тот же бэкфилл по чатам.
- **Список доступных персон у модератора шире, чем список правки** → в «Персонах» карточки без права открываются на чтение, кнопки сохранения нет; в «Воспоминаниях» по-прежнему только правимые персоны.

## Migration Plan

1. `config/001_schema.sql`: колонка `created_by` (`ADD COLUMN IF NOT EXISTS`) и в `CREATE TABLE` для чистых установок.
2. `configurator/001_schema.sql`: таблица `moderator_personas` (`CREATE TABLE IF NOT EXISTS`).
3. Бэкфилл: гранты модераторам на персоны, все чаты которых им уже выданы.
4. Накат на прод — вручную через psql (в репозитории нет CI-наката миграций); после наката проверить ACL и что сохранение персоны проходит под `admin_user`.
5. Откат — `DROP TABLE configurator.moderator_personas`, `DROP COLUMN created_by`; код откатывается revert'ом коммита.
