# Design

## Context

Сейчас админка держит ровно одного принципала: `AdminSecurityConfig` собирает `InMemoryUserDetailsManager` из `BOT_ADMIN_PASSWORD` (`AdminSecurityConfig.java:52`), а все контроллеры включаются условием `AdminPasswordPresentCondition`. Привязка к сети задана одной переменной `server.address=${BOT_ADMIN_BIND:127.0.0.1}` (`application.properties:6`). Меню — статический фрагмент `layout.html`, без модели прав.

Модель данных, которая определяет границы прав: персона глобальная, `chat_personas` связывает её с чатами «многие к одному», а `persona_memories` знает только `persona_id` (`migrations/004_personas_and_memories.sql:61`) — чата в памяти нет. Поэтому «показать модератору память персоны» и «дать править общую персону» — это одно и то же решение, и оно уже принято: правишь персону — видишь её память.

Ограничения проекта: пуш в `main` пересобирает и перезапускает живого бота; схему на прод накатывает сам владелец до пуша; новые таблицы не наследуют права `app_user` и требуют явного `GRANT` (как в `004_personas_and_memories.sql:193`); репозиторий публичный, секретов в конфиге быть не может.

## Goals / Non-Goals

**Goals:**

- Два типа принципалов в одной цепочке Spring Security, без второй формы входа.
- Один компонент, отвечающий на вопросы «какие чаты видны», «можно ли править персону», «кто автор действия»; и проверка прав на сервере, а не скрытием меню.
- Журнал изменений, который пишется в той же транзакции, что и изменение, и переживает удаление учётки автора.
- Восстановление данных персоны и удалённых воспоминаний без восстановления истории чата.

**Non-Goals:**

- Публичный HTTPS, домен, Telegram Login Widget.
- Немедленная инвалидация активной сессии при отзыве доступа.
- Восстановление привязки персоны и стёртой истории чата.
- Управление списком чатов и участниками из админки.

## Decisions

### D1. Владелец остаётся в окружении, модераторы — в базе

`BOT_ADMIN_PASSWORD` продолжает быть и паролем владельца, и выключателем админки. `UserDetailsService` становится составным: логин `admin` обслуживается из окружения с ролью `ADMIN`, остальные — из `admin_accounts` с ролью `MODERATOR`.

Альтернатива — перенести владельца в ту же таблицу и оставить пароль только сидом — отклонена: тогда `BOT_ADMIN_PASSWORD` перестаёт быть выключателем, а требование «Единственный администратор входит по паролю» (`admin-console`) пришлось бы переписывать без пользы для задачи.

Логин `admin` запрещён и проверкой в форме, и ограничением `CHECK` в таблице: одна защита может быть обойдена вторым путём создания учётки.

### D2. Права живут в одном компоненте, а не в контроллерах

`AdminAccess` (сервис) отвечает на три вопроса: `visibleChatIds()`, `canEditPersona(personaId)`, `author()` (ник и имя из `tg_users`). Для владельца `visibleChatIds()` — все чаты.

Правило правления: персона правится, если у неё есть хотя бы одна привязка и **все** её `chat_id` входят в видимые. Проверка — один запрос:

```sql
SELECT count(*) AS total,
       count(*) FILTER (WHERE chat_id <> ALL (:visible)) AS foreign
FROM chat_personas WHERE persona_id = :persona
```

`foreign = 0 AND total > 0` — правит; `foreign > 0` — только чтение. Беспризорных персон не бывает по конструкции: модератор создаёт персону и привязку одной транзакцией (D6), поэтому «нет привязок» — это всегда результат действий владельца, а не модератора.

Фильтрация списков делается в запросах (`findAllWithCounts`, `findAllChats`, `MemoryRepository.search`), а проверка перед изменением — в контроллере. Скрытие пункта меню считается косметикой: тест на прямой GET закрытого раздела обязателен.

### D3. Схема

```sql
CREATE TABLE admin_accounts (
    id serial PRIMARY KEY,
    tg_user_id bigint NOT NULL UNIQUE REFERENCES tg_users(user_id),
    login varchar(64) NOT NULL UNIQUE,
    password_hash varchar(255) NOT NULL,
    created_at timestamptz NOT NULL DEFAULT now(),
    last_login_at timestamptz,
    CONSTRAINT admin_accounts_login_not_admin CHECK (lower(login) <> 'admin')
);

CREATE TABLE chat_moderators (
    chat_id bigint NOT NULL REFERENCES tg_chats(chat_id) ON DELETE CASCADE,
    tg_user_id bigint NOT NULL REFERENCES tg_users(user_id) ON DELETE CASCADE,
    granted_by bigint,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (chat_id, tg_user_id)
);

CREATE TABLE admin_changes (
    id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    at timestamptz NOT NULL DEFAULT now(),
    actor_user_id bigint,
    actor_login varchar(64) NOT NULL,
    entity varchar(32) NOT NULL,          -- persona | binding | memory | account
    entity_id integer,
    chat_id bigint,
    persona_id integer,
    before jsonb,
    after jsonb
);

ALTER TABLE persona_memories ADD COLUMN IF NOT EXISTS deleted_at timestamptz;
```

`actor_user_id` без внешнего ключа и `actor_login` текстом — чтобы журнал не зависел от судьбы учётки. Шаблон выхода обновляется отдельно и только если в нём ещё нет плейсхолдера:

```sql
UPDATE bot_settings SET value = value || ' Убрал: {moderator}'
WHERE setting_key = 'aiPersonaLeaveTemplate' AND value NOT LIKE '%{moderator}%';
```

### D4. Журнал пишется в существующей транзакции

`PersonaRepository.update`/`create` и `switchPersona` уже открывают соединение и транзакцию (`connection.setAutoCommit(false)`). Они получают параметр `Actor` и вызывают `ChangeJournal.record(connection, ...)`, собирая `before`/`after` только из изменившихся полей.

Почему не триггеры: триггер не знает, кто нажал кнопку, — автора пришлось бы передавать через настройку сессии, что хрупче параметра. Почему не аспект на контроллерах: старые значения читаются внутри той же транзакции, а из контроллера это два независимых соединения и шанс, что журнал разойдётся с данными.

Цена решения честная: публичные методы репозитория меняют сигнатуру, и запись журнала обязана участвовать в транзакции — при ошибке вставки правка откатывается вместе с ней (это заявлено в спеке, не побочный эффект).

### D5. Восстановление — это обычная правка

Восстановление персоны читает `before` из записи журнала и прогоняет его через тот же путь `update` с тем же автором. Журнал получает новую запись, а не помечает старую отменённой — история остаётся линейной и читаемой.

Восстановление привязки не предлагается: `switchPersona` уже стёр историю чата, и возврат привязки стёр бы её второй раз. Восстановление воспоминания — это `deleted_at = NULL`.

Обрезка журнала — после вставки, в той же транзакции: у персоны остаются 20 последних записей. Отдельная задача-чистильщик не нужна, объём ограничен самим способом записи.

### D6. Автор в сообщении о выходе

`AdminChatController.assign` получает текущего принципала и достаёт ник и имя из `tg_users` по `tg_user_id`; для владельца — по настройке `ownerChatId`. Подпись собирается тем же `AuthorFormat.sign()`, что и подпись автора в истории, — формат `@ник (Имя)` не расходится между двумя местами.

Плейсхолдер `{moderator}` подставляется только в шаблон выхода; шаблон входа не меняется, и это зафиксировано спекой.

### D7. Предупреждение о стирании истории считается в списке чатов

`findAllChats` получает число сообщений одним соединением:

```sql
LEFT JOIN (SELECT chat_id, count(*) AS messages FROM ai_messages GROUP BY chat_id) m USING (chat_id)
```

Запрос на каждый чат отдельно дал бы N+1 при открытии раздела. Предупреждение показывается рядом с сохранением, когда выбранная персона отличается от текущей; подтверждения вторым шагом нет — предупреждение видно до нажатия, а само сохранение остаётся одним действием.

### D8. Дверь: один слушающий адрес плюс правило файрвола

`server.address` умеет только один адрес, поэтому админка слушает `0.0.0.0`, а доступ ограничивает файрвол: `127.0.0.1` (SSH-туннель владельца) и `10.8.0.0/24` (VPN), остальное — `drop`.

Альтернатива «повесить админку на `10.8.0.1`» отклонена: SSH-туннель владельца ходит на `127.0.0.1`, и он бы перестал работать. Альтернатива «отдельный порт для модераторов» отклонена как лишняя сущность: различие даёт логин, а не адрес.

Профили модераторов собираются из существующего OpenVPN-сервера (`udp 1194`, `tun0 10.8.0.1/24`) **без** `redirect-gateway def1`: иначе весь трафик телефона пойдёт через российский VPS, где Telegram режется DPI, и модератор потеряет доступ к самому боту. В профиле остаётся только туннельная подсеть.

### D9. Сессия и CSRF не меняются

Spring Security продолжает выдавать HttpOnly-сессию и требовать CSRF-токен. Отзыв доступа действует со следующего входа: реестра сессий нет, а немедленное завершение чужих сессий потребовало бы `SessionRegistry` и не покрывает уже открытые вкладки.

## Risks / Trade-offs

- **Правило файрвола не легло вместе с выкаткой** → админка с паролем окажется в интернете. Проверка: `curl` с локальной машины на публичный IP и порт 8081 обязан не соединиться; тест входит в чек-лист выкатки, а не в «потом настроим».
- **`redirect-gateway` остался в профиле** → модератор теряет Telegram и не понимает почему. Проверка перед выдачей: в `.ovpn` нет строки `redirect-gateway`.
- **Пропущенный `deleted_at IS NULL`** → удалённое воспоминание вернётся в промпт. Митигация: чтения памяти идут через ограниченный набор методов репозитория, тест проверяет каждый из них на скрытие удалённых.
- **Модератора застаёт блокировка посреди правки** (персону привязали к чужому чату, пока он редактировал) → сохранение отклоняется. Митигация: карточка общей персоны открывается с явной пометкой «только чтение», а не молча.
- **Сигнатуры репозиториев растут** → вызовы `create`/`update` из неадминских путей пришлось бы тоже снабжать актором. Сейчас такие вызовы есть только у админских контроллеров.
- **Ошибка записи журнала откатывает правку пользователя** → сохранение падает вместо «сохранено без следа». Это осознанный выбор в пользу честного журнала.
- **Обрезка до 20 записей** → старые версии промпта теряются. Приемлемо: цель — вернуть вчерашнее состояние, не вести полную историю.
- **Порядок выкатки** → код без таблиц стартует, но админка падает на входе. Миграция накатывается до пуша (правило проекта), новые таблицы получают `GRANT` в той же миграции.

## Migration Plan

1. Миграция `013_moderator_access.sql`: три таблицы, `deleted_at`, индексы, блок `GRANT` для `app_user`, обновление шаблона выхода.
2. Владелец накатывает миграцию на прод.
3. Локальная проверка сборки: пакет запускается на временном кластере PostgreSQL, админка поднимается, вход владельцем работает.
4. Пуш в `main` → деплой; проверка, что админка владельца отвечает через SSH-туннель.
5. Операции на VPS: сертификаты и профили модераторов без `redirect-gateway`, правило файрвола на 8081, `BOT_ADMIN_BIND=0.0.0.0` в `/etc/telegram-bot/bot.env`, перезапуск сервиса.
6. Откат: вернуть предыдущий коммит и профили без `BOT_ADMIN_BIND`. Таблицы и `deleted_at` аддитивны, но при возврате к жёсткому удалению строки с непустым `deleted_at` нужно либо вернуть, либо удалить руками — старый код их не видит и не удаляет.
