# Spec Delta

## ADDED Requirements

### Requirement: Два исполняемых артефакта

Система SHALL собираться командой `mvn clean package` на JDK 17 в два исполняемых jar: `target/telegram-bot-1.0.jar` для AI-бота и `target/telegram-bot-admin-1.0.jar` для админки. Каждый jar MUST запускаться через `java -jar` без дополнительного classpath и внешних файлов сборки.

#### Scenario: Сборка с нуля

- **WHEN** выполняется `mvn clean package` на JDK 17 в чистом рабочем каталоге
- **THEN** создаются оба jar, содержащие все runtime-зависимости своего приложения

#### Scenario: Запуск бота

- **WHEN** запускается `telegram-bot-1.0.jar` с переменными окружения бота
- **THEN** процесс доходит до регистрации бота в Telegram и не открывает HTTP-порт

#### Scenario: Запуск админки

- **WHEN** запускается `telegram-bot-admin-1.0.jar` с переменными окружения админки
- **THEN** процесс поднимает веб-сервер на `BOT_ADMIN_PORT` и регистрирует своего бота-уведомителя

#### Scenario: Деплой без правок инфраструктуры

- **WHEN** собранные jar копируются на сервер по путям `/usr/bin/tg_bot/` и `/usr/bin/tg_bot_admin/`
- **THEN** юниты `telegram-bot.service` и `telegram-bot-admin.service` запускают приложения без изменения путей, имён файлов или аргументов запуска

## MODIFIED Requirements

### Requirement: Регистрация бота с повторными попытками

Система SHALL регистрировать в Telegram два независимых бота — AI-бота и бота-уведомителя админки — и MUST делать не более трёх попыток регистрации для каждого, логируя номер попытки. Если все попытки одного бота неуспешны, MUST завершаться с ненулевым кодом только его процесс.

#### Scenario: Успешная регистрация не с первой попытки

- **WHEN** первые попытки регистрации бота завершаются ошибкой, а одна из последующих успешна
- **THEN** в лог попадает сообщение об успешном запуске с номером попытки, и этот бот начинает обработку сообщений

#### Scenario: Все попытки неуспешны

- **WHEN** все три попытки регистрации AI-бота завершились ошибкой
- **THEN** процесс AI-бота завершается с ненулевым кодом, а админка продолжает работать

#### Scenario: Два бота не конфликтуют

- **WHEN** оба приложения запущены одновременно
- **THEN** каждое регистрирует свою сессию со своим токеном, и конфликта long polling не возникает

### Requirement: Корректная остановка по SIGTERM

Система SHALL прекращать long polling каждого бота при получении SIGTERM и MUST завершать процесс в пределах `TimeoutStopSec=20` своего юнита. Перезапуск или остановка одного приложения MUST NOT прерывать работу другого.

#### Scenario: Перезапуск юнита

- **WHEN** выполняется `systemctl restart telegram-bot`
- **THEN** предыдущий процесс останавливает опрос обновлений, а новый регистрируется без ошибки конфликта сессии; админка продолжает работать

#### Scenario: Остановка при активном опросе

- **WHEN** SIGTERM приходит AI-боту, пока он ожидает обновления от Telegram
- **THEN** опрос прекращается без ожидания таймаута, и процесс завершается штатно

#### Scenario: Перезапуск админки

- **WHEN** выполняется `systemctl restart telegram-bot-admin`
- **THEN** веб-сервер и бот-уведомитель перезапускаются, а AI-бот продолжает отвечать в чатах

#### Scenario: Остановка админки при активном опросе бота

- **WHEN** админка остановлена, пока AI-бот ожидает обновления от Telegram
- **THEN** AI-бот продолжает опрос и отвечает на сообщения

## REMOVED Requirements

### Requirement: Единственный исполняемый артефакт

**Reason**: Сборка теперь даёт два независимых артефакта — бот и админку, каждый со своим юнитом.

**Migration**: Использовать `telegram-bot-1.0.jar` для бота и `telegram-bot-admin-1.0.jar` для админки; пути деплоя `/usr/bin/tg_bot/` и `/usr/bin/tg_bot_admin/`.
